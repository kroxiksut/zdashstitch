# Ревью предыдущих задач при переходе на Zabbix 8.0

17.11.2026. Область: P0–P6, план, локальные реализации и официальные изменения Zabbix. Это статическое ревью, а не повторный прогон тестов, GUI-приёмка или лабораторная проверка 8.0. Записи о завершённых лабораторных работах 7.4.16 остаются историческими доказательствами своей версии, не становятся доказательствами 8.0 и не обнуляются. Дополняет [Z80-01](Z80-01-version-gap-ru.md).

## Находки по приоритету

1. **Блокер для подключения: P0-04, P2-01.** `AdapterRegistry::resolve` и выбор реестра принимают только `7.4.x` (`crates/zabbix/src/capabilities.rs:210`); без отдельного 8.0-профиля подключение 8.0 не заработает. Оставить предварительную проверку версии до передачи секретов и отказ неподдержанным версиям. Подключение и авторизацию 8.0 проверить отдельно, не ослабляя TLS, CSRF и раздельные gateways.
2. **Блокер для импорта и привязки: P4-01, P2-02, P4-08, P5-01.** `template_import` требует `EXPORT_VERSION = "7.4"` (`crates/template_import/src/lib.rs:29,128`). API reader допускает тип значения только до 5 (`crates/zabbix/src/lookups.rs:785`); 8.0 добавил `value_type=6` JSON для item и itemprototype. Нужны отдельные экспорты 8.0 в YAML/JSON/XML и диагностирование JSON без неявной подмены типом text. Изменение переносимой схемы — O-041. [Изменения API](https://www.zabbix.com/documentation/8.0/en/manual/api/changes).
3. **Версионная привязка доказательств: P0-05/09, P2-05, P3-01/02, P4-07/08, P5.** `VersionedDashboardSnapshot::from_adapter_raw` присваивает `ADAPTER_ID_7_4` (`crates/zabbix/src/snapshot.rs:74`), `CloneMappingState` принимает только 7.4 (`crates/application/src/clone_mapping/storage.rs:47`), а `WorkcopyService` выбирает `WidgetCapabilityRegistry::v7_4()` (`crates/application/src/workcopy/service.rs:360`). Аналогичные прямые вызовы есть в `portable_conversion.rs:470`, `portable_import.rs:22`, `portable_lld_review.rs:268`, `portable_redaction.rs` и `portable_scan.rs`. При добавлении 8.0 нужно явно передавать корректный профиль и хранить его в snapshot/workcopy; проверить переоткрытие прежних данных 7.4 и невозможность принять их за 8.0. Текущий отказ 8.0 закрывает этот путь: это риск ошибочной будущей доработки, а не доказанная текущая запись в 8.0.
4. **Разные API-права и повторная приёмка записи: P1-IN-08/11, P2-01/04/06, P3-01/03, P5-07/08.** `dashboard_create_permission` рассчитана только на 7.4.16 (`crates/zabbix/src/create_permission.rs:108`), включая старое поведение пустого списка. В 8.0 пустой allow list запрещает все методы, но пустой deny list разрешает; новые установки по умолчанию отключают API. Нужны отдельные версия/режим/role fixtures и лабораторная проверка прав, stale plan, единственной записи, read-back, неизвестного исхода и сохранности доступа. Существующий dashboard-only allowlist сохраняется. [Модель роли 8.0](https://www.zabbix.com/documentation/8.0/en/manual/api/reference/role/object), [upgrade notes](https://www.zabbix.com/documentation/8.0/en/manual/whatsnew).
5. **Различия виджетов: P0-09/10, P1-IN-02/04/10, P2-02/04, P3-02, P4-02/03/08, P5.** 8.0 добавляет item-tag поля `svggraph`/`piechart` и другие поля/виджет `scatterplot`; 7.4-реестр не доказывает, что эти поля можно переписывать или безопасно сохранять на 8.0. Нужны версионная матрица, фикстуры и независимые read/write contracts; неизвестное не удалять и не считать поддержанным. [API changes](https://www.zabbix.com/documentation/8.0/en/manual/api/changes).
6. **Существующий пробел масок в GUI: P3-02I, P4-08, P5-01.** Backend требует `acknowledge_visible_outside` при совпадениях вне выбранных узлов (`portable_pattern_review.rs:203`), но `PortablePatternReview.svelte:67` передаёт только `review` и `fingerprint`, а отображает только совпадения внутри выбранных slots (`:100`). Следствие по коду: при внешних совпадениях подтверждение из этого экрана должно быть отклонено; проверка GUI в этом ревью не проводилась. Требуется показывать внешние совпадения и отдельное подтверждение; скрытые правами объекты не объявлять проверенными.
7. **Основная цель пользователя ещё не завершена: P4-02/03, P5-01/02.** Проверка и сохранение привязок, частичная materialization `item`/`clock`, LLD и доказательства масок существуют. Однако `portable_lld_review.rs:285` и `zabbix/src/create.rs:1018` ограничивают portable create типами `item`/`clock`, поэтому график с несколькими узлами и масками не получает план публикации. Это уже существующий остаток P5 для 7.4; отдельно нужны версия-специфичные codec/capabilities и лабораторная приёмка 8.0.
8. **Операционный текст и пользовательские подсказки: P2-01G, P4-01/07.** `lang/ru/template_import.json:2,6` и английский каталог направляют на экспорт 7.4, а `lang/*/offline_builder.json:200,204` честно сообщают, что оценка сделана реестром 7.4. После появления 8.0-профиля сделать информацию о версии явной и локализуемой; до этого не заменять надпись на 8.0 так, будто импорт уже работает.

## Сверка предыдущих этапов

| Этап | Сохраняется и может переиспользоваться | Доработка/приёмка для 8.0 |
|---|---|---|
| P0 | Структура workspace, безопасный ZIP, typed `project/v2`, фундамент VerifiedPlan/journal | Версии, parser, snapshot identity, виджеты, реальные API/права и все write-контракты. JSON-type — отдельное решение. |
| P1 | Карта потоков, локализация, темы, общие макеты и ограничения безопасности | Пересмотреть только зависящие от версии вводы P1-IN-01/02/04/05/08/10/11: ошибки, виджеты, файлы, роли, ownership; статусы `[x]` означают прежний контекст, а не новую приёмку. P1-06 остаётся частичной. |
| P2 | Локальный HTTP/session/CSRF, профиль и защищённый механизм записи | 8.0 read-only, импорт снимка, resolver, ReplaceHost, copy, дифф/конфликт и отправка; заново контракты G2. P2-04G и части экранов уже открыты в плане. |
| P3 | Модель mapping, локальные decisions, intent/журнал и тестовые механизмы | Выбор 8.0-профиля и сохранение mapping, графики/LLD/маски, Clone, права, повторное чтение. G3 принято владельцем для 7.4, не для 8.0. |
| P4 | Автономное редактирование и хранение, библиотека, переносимые пакеты и миграция как общая основа | Парсер 8.0, корректный registry в диагностике и конвертации, новые поля, явный диапазон совместимости, внешние совпадения в GUI. P4-01/03/04/07/08/09 остаются открытыми или частичными в текущем плане. |
| P5 | Привязки item/LLD и ограниченный VerifiedCreatePlan как база | Многосерверные графики, masks, append/update/deployment state, P5-07/08 и всё это независимо для 8.0. |
| P6 | Основы Windows/Linux, локальные настройки и инструменты | Полная сборка, UI и acceptance целевого 8.0 после backend/lab gate; предыдущие тесты и 7.4-сценарии сохранить как отдельную регрессию. |

## Рекомендуемая последовательность

1. Зафиксировать версионный контекст snapshot/workcopy/registry и fixtures 7.4 + 8.0; отдельно решить O-041. Не включать запись 8.0.
2. Ввести read-only 8.0-профиль, авторизацию/ошибки и импорт шаблонов с тестами трёх форматов и отсутствия регрессий 7.4.
3. Обобщить общий код resolver/graph/bindings и сохранение clone state по выбранному адаптеру; доделать безопасный preview/подтверждение масок.
4. На отдельном разрешённом стенде 8.0 доказать операции и P5-07/08 поштучно, затем подключить `VerifiedPlan`, graph и publication только для доказанных возможностей.
5. Провести сквозной GUI и Windows/Linux acceptance для нужных сценариев; документировать границы 7.4 и 8.0 раздельно.

Источники кода проверены непосредственно; XERJ-запросы: `WidgetCapabilityRegistry v7_4`, `AdapterRegistry resolve`, `EXPORT_VERSION`, `dashboard_create_permission`, `project compatibility range`, `validate_portable_widget_for_create`. Индекс был устаревшим. Production, лаборатория, сборки и GUI в ходе этого ревью не использовались.
