# Входные данные backend для дизайна (P1-IN)

**Статус:** результаты исследований P1-IN-01—09 от 2026-10-24, P1-IN-11 от 2026-10-25 и лабораторных контрактов LAB-02 от 2026-10-28 (их панели оставлены на лаборатории, см. раздел LAB-02). Это факты о поведении Zabbix и текущего стека, а не реализация функций и не дизайн-приёмка. Лабораторные данные получены на синтетической лабораторной Zabbix **7.4.16** (PostgreSQL, Apache), клиенты — Windows 10 и Linux (Ubuntu 26.04 с рабочим столом GNOME, Ubuntu 24.04 в WSL). Адреса, имена хостов, учётные данные и содержимое объектов в документ не включены. Все созданные пробами объекты удалены, глобальные настройки восстановлены.

Связанные решения: O-016 (что можно делать до G1), O-017 (локальная сессия), O-018 (локальное хранилище), O-023 (выбор файлов). Задачи-потребители указаны в `TASKS_RU.md` строками «Вход backend».

## P1-IN-01 — таксономия ошибок подключения и авторизации

**Статус:** выполнено для клиентов Windows 10 и Linux (Ubuntu 26.04, Ubuntu 24.04 в WSL), включая вход через LDAP. Astra Linux и RED OS не проверялись: их glibc старше той, под которую собрана проба; проверка отложена по решению владельца. Воспроизведение: `crates/zabbix/tests/lab_error_taxonomy.rs` (opt-in, `#[ignore]`) и синтетические TLS-стенды с сертификатами, сгенерированными для теста. На Linux проба запускалась с `LANG=C` и `LANG=ru_RU.UTF-8`, результаты совпали.

### Сторона transport (reqwest 0.13 + rustls)

| Код (предложение) | Шаг проверки | Windows | Linux | Retry |
|---|---|---|---|---|
| `dns_unresolvable` | endpoint | connect-ошибка с ОС-кодом 11001 | connect-ошибка стадии `dns error` **без ОС-кода** (`getaddrinfo`: `Name or service not known`); различать по стадии подключения, а не по тексту | да, после исправления адреса |
| `connection_refused` | endpoint | `ErrorKind::ConnectionRefused` (10061) | `ErrorKind::ConnectionRefused` (errno 111) | да |
| `host_unreachable_or_timeout` | endpoint | `ErrorKind::TimedOut` (10060): таймаут соединения ОС срабатывает раньше общего таймаута transport 30 с | сразу `ErrorKind::HostUnreachable` (errno 113) **или** таймаут — зависит от сети, на одном адресе в разных прогонах выходило по-разному | да |
| `wrong_base_path` | API reachability | HTTP 404 | HTTP 404 | нет, нужна правка адреса |
| `redirect` | API reachability | HTTP 301 (base path без `/` в конце); редиректы transport не выполняет | так же | нет, нужна нормализация адреса |
| `not_jsonrpc` | API reachability | ответ 200, но не JSON (`InvalidResponse`) | так же | нет |
| `not_jsonrpc` (plain HTTP на TLS-порт) | endpoint | `IncompleteMessage` | `ConnectionReset` (errno 104) или ошибка разбора ответа `Parse(Version)` — зависит от сервера | нет |
| `tls_untrusted` | TLS | `InvalidCertificate(UnknownIssuer)` | так же | после добавления корня |

Неразличимые случаи объединены: недоступный хост и таймаут — один код; plain HTTP на TLS-порт, не тот путь, прокси и страница входа — один код `not_jsonrpc` («по адресу нет Zabbix API»). Самоподписанный сертификат и сертификат неизвестного CA неразличимы на обеих ОС.

После добавления корня (`tls_certs_merge` поверх системного хранилища; `tls_certs_only`):

| Случай | merge, Windows (системный верификатор) | merge, Linux | only (webpki), обе ОС |
|---|---|---|---|
| имя не совпадает | `NotValidForName` | `NotValidForNameContext` с ожидаемым и предъявленным именем | `NotValidForNameContext` |
| истёк | `Expired` | `ExpiredContext` | `ExpiredContext` |
| ещё не действителен | **`Expired`** — неотличим от истёкшего | `NotValidYetContext` | `NotValidYetContext` |
| самоподписанный | `UnknownIssuer` | `UnknownIssuer` | `UnknownIssuer` |

Вывод для P1-02F: один код `tls_certificate_time_invalid` («сертификат недействителен по сроку») без разделения «истёк / ещё не действителен» — на Windows в режиме merge их не различить. Если различие доступно, его можно показать в технических деталях, но не как отдельное состояние экрана.

Тексты ошибок ОС: на Windows приходят на языке системы (на русской Windows — по-русски), на Linux — всегда по-английски, даже при `LANG=ru_RU.UTF-8`, потому что Rust-процесс не вызывает `setlocale`. Ни в одном случае текст ОС не годится ни для классификации, ни для показа пользователю; в технических деталях допустимы код ошибки и стадия (`dns`, `connect`, `tls`, `http`, `jsonrpc`).

### Сторона Zabbix (API 7.4.16)

| Случай | Код / сообщение API | Различимость |
|---|---|---|
| Неверный пароль, неизвестный пользователь, временная блокировка (5 попыток, 30 с) | `-32500` `Incorrect user name or password or account is temporarily blocked.` | **неразличимы** между собой |
| Пользователь в отключённой группе | `-32602` `No permissions for system access.` | да |
| Роль без доступа к API | вход **успешен**, первый вызов: `-32500` `No permissions to call "<method>".` | да, но только на первом вызове |
| Неверный или отключённый API-токен | `-32602` `Not authorized.` | неверный и отключённый неразличимы |
| Истёкший API-токен | `-32500` `API token expired.` | да |
| MFA (TOTP) у пользователя | `user.login` возвращает строку, первый вызов: `-32602` `Session terminated, re-login, please.` | да, но только на первом вызове |
| Проверка токена | `user.checkAuthentication {token}`: валидный — данные пользователя, невалидный — `Not authorized.` | годится как явный шаг «проверка авторизации» |
| LDAP: успешный вход | `user.login` возвращает сессию, первый вызов работает | — |
| LDAP: неверный пароль; пользователь есть в Zabbix, но нет в каталоге; есть в каталоге, но нет в Zabbix; неверный пароль служебной учётной записи; LDAP-сервер остановлен; LDAP-сервер недоступен по сети | все `-32500` `Incorrect user name or password or account is temporarily blocked.` | **неразличимы** между собой и с ошибкой внутреннего пароля; недоступный сервер отвечает через ~7 с вместо ~1 с |
| Внутренний пользователь при неработающем LDAP | вход успешен | да |

LDAP проверен на непривилегированном тестовом каталоге GLAuth 2.5.4 на loopback лабораторной VM; каталог Zabbix создавался через API и удалён, настройки аутентификации восстановлены. Различить причины отказа LDAP может только администратор через `userdirectory.test`, обычному пользователю этот метод недоступен. Для дизайна P1-02C/D: одно сообщение об ошибке входа с подсказкой, что при входе через LDAP та же ошибка возникает при недоступности каталога; долгий ответ (больше нескольких секунд) — повод показать индикатор ожидания, а не отдельный код.

### Найденные дефекты и требования к P2-01

- `ZabbixClient::authenticate` с API-токеном не делает серверной проверки; неверный токен обнаруживается позже.
- `ZabbixError::is_permission_denied` относит `Not authorized.` к нехватке прав, поэтому неверный токен выглядит как «все методы запрещены». Нужно различать `Not authorized.` / `Session terminated…` (авторизация) и `No permissions to call…` (права роли).
- Шаг проверки авторизации после входа обязателен: роль без API и MFA проявляются только на первом вызове.

### Запуск на рабочем сервере (только владелец)

Тест `lab_read_only` вызывает только read-методы (`apiinfo.version`, `template.get`, `host.get`, `item.get` с `limit: 1`, `dashboard.get`, `graph.get` с `limit: 1`, при входе по паролю — `user.login`/`user.logout`) и печатает только счётчики, коды типов полей, распределения и длины имён. Имена, ID, хосты и содержимое объектов не печатаются. Порядок для владельца:

1. Взять учётную запись или API-токен с ролью только на чтение и правами на нужные панели (что не видно по правам, в агрегаты не попадёт, см. P1-IN-08).
2. Задать `ZDASHSTITCH_LAB_ACK=read-only-authorized-7.4`, `ZDASHSTITCH_LAB_API_URL` и либо `ZDASHSTITCH_LAB_API_TOKEN`, либо `ZDASHSTITCH_LAB_USERNAME`/`ZDASHSTITCH_LAB_PASSWORD`; запустить `cargo nextest run -p zdashstitch-zabbix --run-ignored only --no-capture lab_read_only`.
3. Перед передачей проверить вывод: в `widgets_by_type` могут оказаться идентификаторы сторонних модулей виджетов; их при необходимости заменить на «module-N».

## P1-IN-03 — модель статусов resolver

**Статус:** выполнено (спецификация на лабораторных данных).

Доступное evidence из `item.get`: `key_`, `name`, `value_type`, `units`, `flags` (0 — обычный, 4 — найден LLD), `templateid` (унаследован от шаблона), `itemDiscovery` (родительский прототип). Шаблоны `svggraph` сопоставляются по **имени** item, не по ключу.

Два хоста на одном шаблоне Linux: у источника 84 items, у цели 100. Ключей совпало точно — 66, все с одинаковыми `value_type` и `units`. Отсутствуют на цели — 18, и **все 18 — элементы LLD**. Шаблон имени `CPU utilization` даёт 1 совпадение, маска `CPU*` — 11.

Предлагаемые независимые оси:

| Совпадение | Когда | Evidence для UI |
|---|---|---|
| `exact` | тот же `key_` на цели, совпадают `value_type` и `units` | ключ, тип, единицы, шаблон-источник |
| `compatible` | тот же `key_`, но отличаются `units` или происхождение | что именно отличается |
| `ambiguous` | шаблон имени или маска даёт несколько кандидатов | список кандидатов |
| `missing` | на цели нет ключа и он не из LLD | — |
| `unresolved_lld` | ключ источника — элемент LLD, а на цели такого экземпляра нет | родительский прототип, ключ с макросами |
| `denied` | объект не виден правами (неотличимо от отсутствия, см. P1-IN-08) | только «не найдено или нет доступа» |

| Пригодность | Когда |
|---|---|
| `editable` | тип виджета и поле подтверждены контрактом записи (P1-IN-04) |
| `read_only` | ссылка понятна, но запись не подтверждена |
| `unsupported` | неизвестный виджет или поле |

## P1-IN-04 — матрица write-возможностей 7.4.16

**Статус:** выполнено на временных тестовых панелях (созданы и удалены). Контрактные Rust-тесты для реализации — P2-06A и P2-04A.

Отдельный прототип вне репозитория: локальный HTTP-сервер на loopback по нажатию кнопки в браузере открывает диалог `rfd` 0.17.2 (открыть файл, выбрать каталог, сохранить как) и возвращает браузеру только имя файла и признаки (существует, symlink, отличие канонического пути, сетевой путь); полный путь остаётся в процессе.

| Наблюдение | Windows 10 | Ubuntu 26.04 (GNOME, Wayland) |
|---|---|---|
| Зависимости | 6 крейтов, без системных библиотек | с фичами по умолчанию нужен `libwayland-client` (dev-пакет) уже при сборке; с одной фичей `xdg-portal` — 7 крейтов без системных библиотек |

Выводы для дизайна (O-031):

- Выбор владельца возможен только у Super admin; остальным поле не показывается, а `userid` не отправляется никогда — иначе не владелец с правом записи незаметно забирает владение.
- Обновление панели без полей доступа сохраняет владельца и доступ. Поля `private`, `userid`, `users`, `userGroups` передаются только при явном изменении доступа.
- Получателей доступа можно выбирать только из того, что видит учётная запись подключения (`user.get`, `usergroup.get`).
- Для не-Super admin список доступа всегда может быть неполным, а запись заменяет его целиком. Перезапись доступа существующей панели такой учётной записью может молча удалить чужие записи; копия доступа при клонировании может быть неполной.
- Правка, которая лишает пользователя собственного права записи, должна блокироваться до отправки.

### Главная находка: порядок полей виджета при чтении не определён

- По исходникам 7.4.16 (`CDashboardGeneral::addRelatedObjects`) `dashboard.get` сортирует страницы по `sortorder`. Строки `widget` и `widget_field` он выбирает через `DB::select` без `ORDER BY`, то есть в физическом порядке строк таблицы.
- `dashboard.update` (`updateWidgetFields`) сопоставляет поле с сохранённым по паре (`type`, `name`). Изменённое значение записывается через `UPDATE` той же строки: `widget_fieldid` сохраняется, это проверено чтением БД. Неизменённые поля не трогаются. В PostgreSQL обновлённая строка получает новое физическое место, поэтому при следующем чтении поле стоит в другой позиции массива `fields`.
- Во всех трёх контрактах `update` прочитанный документ **не совпал побайтно** с ожидаемым. Расходится только порядок `fields` у изменённых виджетов. Если сравнивать поля как множество по `name` и `type`, документ совпадает полностью, включая страницы, виджеты, их ID и порядок. Обычно изменённые поля уходят в конец массива, но в одном из двух прогонов `svggraph` вышло иначе: место зависит от свободного места на странице таблицы.
- Следствие для кода: `VerifiedDashboardUpdate::matches_expected` сравнивает отпечаток снимка, а он считается по сырому JSON вместе с порядком полей. Тесты сравнили отпечаток ожидаемого документа (`from_adapter_raw`) с отпечатком прочитанного: во всех трёх контрактах он **не совпал**. Значит, сейчас закрытый путь публикации после успешной записи вернёт `FailedAfterResponse`: повторной отправки нет, но успех не подтверждается. Это касается и P0-07: у панели `ZDashstitch Contract Lab` после замены `itemid` поле `itemid.0` сейчас хранится последним.
- Виджеты тоже читаются без `ORDER BY`. В контрактах строки `widget` не менялись, так как менялись только значения полей, и порядок виджетов сохранился. Изменение геометрии или имени виджета может так же переставить виджеты при чтении — это не проверялось.
- Сразу после `dashboard.create` поля читаются в порядке отправки.

У глобальных панелей `uuid` — пустая строка: ключ есть в `output: extend`, но запросить его явно в `output` нельзя (`value must be one of "dashboardid", "name", "userid", "private", "display_period", "auto_start"`). ### Предложения для кода (решают задачи P2-04/P2-06)

1. До переключения любого флага сделать проверку read-back (`matches_expected`) и сравнение перед отправкой каноническими. Поля каждого виджета сравнивать как множество, отсортированное по `name` и `type`. Страницы сравнивать по порядку, виджеты сопоставлять по `widgetid`. Без этого успешная запись не подтверждается.
2. После п. 1 для 7.4.16 можно переводить в `Supported` контракты `update_several_pages`, `svggraph_dataset_itemids`, `svggraph_dataset_hosts` (только точное имя без `*`; маски, как и сейчас, отклоняются) и `classic_graph_graphid`, а также добавить `graph` в `RESEND_PROVEN_WIDGET_TYPES`.
3. Для `dashboard.create` подтверждены приватность по умолчанию, владелец, умолчания и копирование «как прочитано». Сервер принимает любые типы виджетов, включая незарегистрированные, так что какие виджеты копировать, решает адаптер (ADR-011). Сверку неизвестного исхода `create` нужно доказать отдельно.
4. Предварительная проверка имени должна учитывать регистр так же, как сервер (на PostgreSQL — с учётом регистра), и не может доказать, что имя свободно.

### Повторный прогон после канонического отпечатка (28.10.2026)

Предложения 1–4 реализованы в адаптере, описание — в `adapter_contract_v1_ru.md`, дополнение от 28.10.2026. После этого три тестовых бинарника прогнаны на той же лаборатории по одному, в таком порядке: `lab_write_contracts`, `lab_verified_publish`, `lab_write_contracts_p2`. Все прошли.

- Тесты `update` в `lab_write_contracts_p2` теперь пишут через закрытый путь адаптера: `verify_widget_field_replacements`, затем `publish_verified_dashboard_update`. Итог во всех трёх контрактах — `Verified`, ровно одна отправка. Канонический отпечаток ожидаемого документа равен отпечатку прочитанного, отпечаток байтов — нет. Порядок полей снова изменился: в `svggraph` изменённые поля в этот раз оказались не в конце.
- В классическом `graph` после добавления `graph` в `RESEND_PROVEN_WIDGET_TYPES` неподтверждённых виджетов нет.
- `create`: `create_private_dashboard` и `create_copy_read_widgets` проходят. На момент этого прогона адаптер всё равно не строил создание: был нужен непроверенный `create_reconcile_unknown_outcome` (доказан в следующем подразделе). `dashboards_named` возвращает только имя с точным регистром.
- P0-07 (`lab_verified_publish`) перед изменением прошёл лишь потому, что изменяемое поле `itemid.0` уже стояло последним. `lab_write_contracts` возвращает виджету порядок `itemid.0, reference, show.0`. После публикации порядок читается как `reference, show.0, itemid.0`, и старая проверка по байтам дала бы `FailedAfterResponse`.
- Новая проба `duplicate_widget_field_names_are_probed` (панель `— duplicate field names` оставлена): `dashboard.create` **принимает** виджет с двумя полями одного `name` — и того же `type`, и разного. Оба поля читаются обратно. Значит, уникальность имени поля внутри виджета сервер не гарантирует. Канонический отпечаток сравнивает поля как мультимножество, а адаптер отказывается переотправлять такой виджет (`field_ambiguous`).

После прохождения `create_reconcile_unknown_outcome` переведён в `Supported` для 7.4.16. Теперь `CreateContract::COPY` выполним для копии виджетов, известных реестру адаптера. Пользовательского маршрута создания нет.

**`sharing_lists_are_read_as_sets` — пройден.** Панель доступна двум тестовым пользователям и двум тестовым группам (в выводе — метки «low»/«high» по возрастанию ID, без самих ID).

- При создании отправлено `[high:2, low:3]` (ID, право) для пользователей и групп. Прочитано в порядке отправки: `[high:2, low:3]`. Повторное чтение побайтно то же. Значит, строки не упорядочены по ID: это порядок вставки.
- У первой записи изменено право (`high` 2 → 3), порядок отправки тот же. Прочитано `[low:3, high:3]`: изменённая запись переместилась в конец, как изменённые поля виджета.
- Тот же набор отправлен в обратном порядке без изменения прав. Прочитанный документ побайтно равен предыдущему: сервер ничего не переписал.
- Это то же поведение, что у строк `widget_field`: порядок чтения не определён. Исходники 7.4.16 для `dashboard_user` и `dashboard_usrgrp` в этот раз не сверялись; вывод сделан по наблюдению. Канонический отпечаток теперь сравнивает `users` по `userid`, а `userGroups` по `usrgrpid` и `permission` как множества (`adapter_contract_v1_ru.md`, дополнение 28.10.2026, п. 2). Тест требует, чтобы отпечаток ожидаемого документа совпадал с прочитанным при любом порядке списков и отличался после смены права.

**Адресация по `widgetid` (код, без лаборатории).** Замены полей теперь адресуются парой (позиция страницы, `widgetid`). Перед отправкой адаптер строит запрос заново из чтения, сделанного в этот момент, поэтому виджеты уходят в порядке сервера. На лаборатории порядок виджетов в этих прогонах не менялся, это покрыто mock-тестами: Remote с переставленными виджетами и полями даёт план без `widget_identity_mismatch`, запрос уходит в порядке последнего чтения, итог — `Verified`.

**ReplaceHost для классического `graph` (P2-02F, код).** Раз `classic_graph_graphid` — `Supported` для версии Base (7.4.16), `graphid.<n>` виджета `graph` редактируем. Он заменяется на график того же имени и того же шаблона на целевом узле. Если на целевом узле есть только график того же имени из другого шаблона или без шаблона, совпадение лишь `compatible` и само не применяется: `origin_differs` блокирует изменение и требует решения. Для других версий остаётся `unsupported` с `classic_graph_contract_pending`. Элемент данных простого графика (`source_type=1`, `itemid.<n>`) остаётся на старом узле с `field_not_replaceable`: LAB-02 доказал только его неизменную переотправку, а не замену.
