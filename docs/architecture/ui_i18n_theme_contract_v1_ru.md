# Контракт UI, локализации и тем v1

**Статус:** принято владельцем 24.10.2026, решение O-010. Контракт обязателен для пользовательских сообщений из Rust/Axum, TypeScript и Svelte и для дизайнов MVP.

## 1. Граница пользовательского текста

- Любой текст, который может увидеть пользователь, задаётся через стабильный `message_id` и параметры. Это относится к заголовкам, кнопкам, подсказкам, ошибкам, предупреждениям, уведомлениям, состояниям загрузки/пустого результата, подтверждениям, accessibility-текстам, meta description и сообщениям нативной оболочки.
- Rust/application/Axum возвращают в UI машинный код, безопасные параметры и уровень сообщения, но не готовую локализованную фразу. Svelte/TypeScript не выводят сырые enum/status/error значения как пользовательский текст.
- Исключения — пользовательские и серверные данные: названия панелей, страниц, хостов, шаблонов, метрик и прочие значения из Zabbix не переводятся. Сырые ответы сервера не становятся основной локализованной ошибкой и показываются только как безопасно очищенные технические подробности, когда это разрешено.
- Технические логи приложения, диагностические идентификаторы, имена ключей/полей и комментарии рабочих конфигурационных файлов пишутся только на английском.
- Локализованные комментарии допустимы в отдельных файлах примеров, например `config.example.en.*` и `config.example.ru.*`; рабочий формат и имена ключей остаются одинаковыми и англоязычными.

## 2. Каталоги и языки

Канонические data-only каталоги размещаются в корне репозитория:

```text
lang/
├── en/
│   ├── manifest.json
│   ├── common.json
│   ├── startup.json
│   ├── connection.json
│   ├── dashboards.json
│   ├── replace-host.json
│   ├── publication.json
│   └── errors.json
└── ru/
    └── те же пространства имён
```

- Английский (`en`) — исходный и обязательный каталог, определяющий набор ключей и параметры сообщений.
- Русский (`ru`) — обязательный полный перевод MVP. Для отсутствующего ключа runtime безопасно использует английский, но проверка полноты поддерживаемого языка должна завершаться ошибкой до релиза.
- Файлы делятся по функциональным пространствам имён и могут загружаться потребителями независимо. Компоненты зависят от типизированных ключей, а не от расположения конкретного JSON-файла.
- Каталоги не содержат исполняемого кода, выражений, HTML или произвольных сетевых ресурсов. Параметры экранируются потребителем; набор и типы placeholders совпадают с английским источником.
- Форматирование чисел, дат, времени и множественного числа учитывает locale; предложения не собираются конкатенацией переведённых фрагментов.

### 2.1. Типы параметров и форматы сообщений

Решение O-035 (26.10.2026). Каждый параметр сообщения объявляется в `placeholders` одним из типов; `tools/build_i18n.py` отвергает любой другой тип и несовпадение объявленных и использованных параметров.

| Тип | Значение | Отображение |
|---|---|---|
| `text` | пользовательские и серверные данные или уже переведённый текст | как есть, без перевода |
| `technical` | технический идентификатор: версия, метод API, поле, тип виджета | как есть |
| `technical_optional` | технический идентификатор, которого может не быть (например, открытая верхняя граница диапазона версий) | отсутствующее значение — маркер «—» |
| `number` | число | `Intl.NumberFormat` по locale; аргумент ICU `plural` всегда `number` |
| `date` | дата | `Intl.DateTimeFormat` по locale |
| `datetime` | дата и время | `DATE_TIME_FORMAT` по locale в локальном часовом поясе пользователя |

- Множественное число — стандартный ICU `plural` с обязательной веткой `other` и категориями CLDR языка (`en`: `one`, `other`; `ru`: `one`, `few`, `many`, `other`); точные совпадения `=N` допустимы дополнительно.
- Выбор по значению — только стандартный ICU `select`: аргумент обязателен (в сгенерированных типах TypeScript он не опциональный) и объявлен `text` или `technical`, ветка `other` обязательна. Значение без собственной ветки, в том числе отсутствующее, выбирает `other`; отсутствующий параметр внутри ветки показывается маркером «—», как у остальных типов. Пустого вывода для отсутствующего аргумента нет.
- **Необязательная часть фразы — отдельный message ID, а не пустая ветка.** Например, «собрана из N страниц» и «собрана из N страниц: источники» — два сообщения (`draft.provenance.assembled` и `draft.provenance.assembled_with_sources`); выбор между ними делает вызывающий код.
- Даты и время application API передают строкой RFC 3339 в UTC (например, `2026-10-26T07:33:20Z`). UI разбирает её общим помощником `parseTimestamp` и форматирует по `DATE_TIME_FORMAT` в locale и часовом поясе пользователя; сервер никогда не присылает отформатированную дату. Неразборчивое или отсутствующее значение показывается маркером «—», а не «Invalid Date».
- Тип виджета application API передают техническим идентификатором (например, `svggraph`). UI переводит его через сообщение `widget.type.<id>`, а для неизвестного типа показывает сам технический идентификатор; результат передаётся в сообщение как параметр `text` (например, `{type}` в `draft.structure.widget_geometry`).

## 3. Терминология Zabbix

- Для пользовательских терминов используется официальная терминология локализации целевой ветки Zabbix 7.4, если перевод там устойчив и применим в том же смысле.
- Не переводятся названия продукта, API-методы и поля, технические идентификаторы, item keys, macros, widget type IDs и термины, которые официальный интерфейс Zabbix оставляет на английском.
- Неоднозначные решения фиксируются в проектном glossary; нельзя молча вводить новый русский эквивалент для уже принятого термина.
- Допустимо сверяться с upstream-локалями для терминологии, но нельзя копировать целые сторонние каталоги переводов без проверки лицензии и происхождения.

## 4. Переводы как отдельный вклад

- Переводы принимаются отдельными pull request без изменений Rust/TypeScript/Svelte, build scripts или контрактов. Если нужен код, он выносится в отдельный технический pull request.
- Для `en` и `ru` обязательны полнота, согласованная терминология и продуктовая проверка.
- Новый язык может быть принят как `experimental` с английским fallback и более лёгкой лингвистической проверкой. Это не ослабляет автоматические проверки структуры, placeholders, формата, безопасности и лицензии.
- Перевод не вправе менять смысл предупреждения, ослаблять сообщение о риске или скрывать неподдерживаемую возможность. Такие изменения рассматриваются как продуктовые, а не переводческие.
- Runtime-каталоги являются code-like data и принимаются под `MIT OR Apache-2.0`; перевод документации сохраняет лицензию документации `CC-BY-4.0`.

## 5. Темы и дизайн

- Темизация строится на семантических design tokens. Компоненты не содержат собственных литералов цветов для состояний интерфейса.
- Поддерживаются `system`, `light`, `dark` и `high_contrast`; выбор пользователя хранится локально — в файле настроек `zdashstitch-settings/v0` через локальный сервер, не в браузерном хранилище. Цвет не является единственным носителем статуса.
- `high_contrast` (28.10.2026, решение владельца O-038) — собственная тема приложения на светлой основе: текст не ниже 7:1, границы, рамка фокуса и линии сетки не ниже 4.5:1 к поверхностям, рамка фокуса толще (3 px), без декоративных теней; текущее место в навигации дополнительно подчёркнуто. Режим контрастности ОС (`forced-colors`) по-прежнему учитывается и важнее любой темы, включая `high_contrast`. Значения токенов — P1-00C §3.1; проверка — `tests/test_ui_tokens.py`.
- Токены покрывают surfaces, текст, границы, действия, focus, overlay, тени и семантические состояния success/info/warning/danger. Обязательны контраст, клавиатурный focus, reduced motion и пригодность к системному high-contrast режиму.
- Проверочные макеты выполняются только на русском языке с терминами официальной русской локализации Zabbix; английские строки и их длина проверяются по словнику P1-00F и тестами P2-00, а не в макетах.
- Все макеты P1, включая единый экран preview/diff/conflict/publication (`P1-08`), проектируются только в светлой теме; тёмного эталонного макета нет. Тёмная тема проверяется в работающем приложении: render/accessibility-проверки и ручная приёмка экранов, начиная с «Публикации» как экрана с наиболее широким набором таблиц, статусов и блокирующих диагностик (решение владельца 26.10.2026 (вечер), В-9).
- Интерфейсные, статусные и tray-иконки на всех платформах выбираются только из outline-набора Tabler Icons; самодельные пиктограммы, перерисованные варианты и смешение icon libraries запрещены. Имя upstream-иконки фиксируется в handoff/инвентаре, смысл задаётся локализуемой label отдельно от изображения. Собственный логотип приложения и Стежик не относятся к Tabler; provenance и MIT notice Tabler хранятся в `assets/icons/THIRD_PARTY.md` и показываются в окне лицензий.

## 6. Приёмка UI-задач

Перед приёмкой пользовательского компонента проверяются: отсутствие захардкоженных отображаемых строк, полнота `en`/`ru`, совпадение placeholders, рендер обоих языков, обе темы, клавиатурный focus, отсутствие зависимости смысла только от цвета, корректное отображение длинного текста и использование только зарегистрированных Tabler outline icons с доступными именами. Технический лог остаётся английским и не считается UI-каталогом.
