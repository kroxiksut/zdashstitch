# Контракт файлов v1 (редакция v0.6)

Источники: `schemas/*.schema.json` (структура), ADR-012 (семантика), эталонный валидатор и тесты (примеры). «v1» описывает **наш формат**, а не поколение Zabbix. Расширения в v1 только обратно совместимые; несовместимые изменения требуют `/v2` и явной миграции.

> **O-025/O-026/P0-08:** UI оперирует локальным черновиком одной панели либо одной страницы (инженерное имя — typed Dashboard/Page project; в интерфейсе слово «проект» и имя формата не показываются). `zdashstitch.project/v2` реализует один typed root; `project/v1` остаётся читаемым legacy multi-dashboard container и мигрируется только с явным выбором root. См. [`domain_model_v1_ru.md`](domain_model_v1_ru.md).

| Файл/ресурс | Формат | Переносится | Создаётся когда |
|---|---|---|---|
| `project.yaml` | `zdashstitch.project/v2` | Да | Typed Dashboard/Page project; в архиве фиксированное имя |
| legacy `project.yaml` | `zdashstitch.project/v1` | Да, только чтение/явная миграция | Legacy multi-dashboard container |
| `metrics/*.yaml` | `zdashstitch.metrics/v1` | Да, после классификации | Импорт и нормализация шаблонов |
| `bindings.local.yaml` | `zdashstitch.local-bindings/v1` | **Нет** | В закрытом контуре после выбора hostid |
| `deployment.local.yaml` | `zdashstitch.deployment-state/v1` | **Нет** | После проверенной публикации и повторного чтения |
| API snapshot, рабочая копия импортированной панели, журнал операций | Внутренние `zdashstitch.raw-snapshot/v0`, `zdashstitch.workcopy/v0`, `zdashstitch.journal/v0` в каталоге данных пользователя (ADR-012 D-11) | **Нет** | Импорт с сервера, локальные изменения импортированной панели, каждая попытка публикации |

## Контейнер передачи

Один ZIP с `project.yaml` и **ровно** перечисленными в `catalogs[].file` файлами из `metrics/`. Запрещены внешние ссылки, каталоги вложений, CSS/JS, лишние файлы и относительные выходы из области пакета. ZIP не должен содержать `bindings.local.yaml` даже при экспорте из уже связанного проекта. Образцы: `examples/db-pilot.yaml` и `examples/db-pilot-package.zip`. Последний — **синтетический**, не документ Zabbix.

## Typed project/v2

- `kind` принимает только `dashboard` или `page`; `root` содержит соответственно один Dashboard или одну Page.
- `declared_compatibility.minimum` — включённая нижняя граница, `maximum_exclusive` — необязательная исключающая верхняя. Это заявление автора, не capability gate записи.
- `provenance.kind` — `local`, `migrated_v1` либо `server_snapshot`. Для миграции сохраняются только логические source IDs и legacy format; server/connection/target IDs не переносятся.
- Target intent отсутствует в schema. `CreateDashboard`/`AppendPage` и конкретная цель принадлежат application plan и локальному состоянию.
- `catalogs` и `roles` могут быть пустыми: черновик без метрик (например, страница только с часами) остаётся корректным. Для legacy `project/v1` прежний минимум в один каталог и одну роль не меняется.
- Виды `graph` и `item_value` сохранены без изменения для совместимости с P0-08. Общий вид `type: zabbix` хранит `widget_type`, имя, геометрию и не более 1024 полей `{name, field_type, registry_state, value}`. `field_type` — числовой `ZBX_WIDGET_FIELD_TYPE_*` (0–13 известны 7.4; 14–65535 допустимы только как явно `unknown`).
- Простые значения 0/1 хранятся как целое/строка. Ссылки 2–13 не содержат server ID: host/group и item/prototype могут быть переносимой ролью/слотом или метрикой каталога, остальные сохраняются как `unresolved` с видом объекта и отображаемым именем. Неизвестный тип поля хранится только как `unresolved/unknown`; `reference` остаётся обычным строковым полем.
- `registry_state: unknown` сохраняет неизвестный реестру тип или поле, но не выдаёт право на изменение. Перед созданием application повторно сверяет реестр адаптера: неизвестное поле/тип или unresolved-ссылка — blocker до построения плана публикации.
- Поле `type: zabbix` хранит ровно один объект Zabbix. Поэтому `selection: all` в значении host и в `metric.hosts` допустим только для роли с `cardinality: one`; для `many` нужен именованный `slot` (код `widget_single_reference_multi`). Метрика каталога с `value_type: binary` в поле типа 4 (элемент данных) отклоняется кодом `binary_item_value`, как и для Item value.
- Пределы общего вида (`widget_type` по шаблону `^[a-z][a-z0-9._-]{0,127}$` — `widget_type`, имя ≤ 200 — `widget_name`, ≤ 1024 полей — `widget_field_count`, имя поля 1–255 символов без управляющих — `widget_field_name`, строковое значение ≤ 16384 — `widget_field_value`, тип ≥ 14 без `registry_state: unknown` — `unknown_field_type_state`, несовпадение значения и типа — `widget_field_value_kind`) проверяются до JSON Schema одинаково в Python-эталоне и Rust и дают одинаковые коды на общих фикстурах `fixtures/formats/v2/negative-cases.json`.
- Правило создания из переносимого черновика (application, до плана публикации): виджет и все поля помечены `known`, тип поля 0–13, ни одной `unresolved`-ссылки; для типов с проверенным кодеком создания (`item`, `svggraph`, `clock`, `problems`) имена полей должны быть в реестре адаптера. `item` требует `itemid.0`, `svggraph` — хотя бы один набор `ds.N` с узлами и элементами (`ds.N.hosts.M` + `ds.N.items.M`) либо `ds.N.itemids.M` (код `portable_widget_required_fields_missing`). `clock` и `problems` допускают пустой набор полей. Прочие распознанные типы (`gauge`, `tophosts`, `honeycomb`, …) допускаются только с непустым набором полей; имена полей реестру знать не обязательно; пустой набор — `portable_widget_incomplete`.
- Остаточный риск: формат не хранит признак «набор полей получен целиком из исходного виджета» (`provenance.kind` — только `local`, `migrated_v1`, `server_snapshot`). Непустой, но урезанный набор полей распознанного типа без кодека создания schema и application отличить не могут; сервер Zabbix такой виджет примет, и он может отображаться неполно.
- Строковые (1) и целые (0) поля могут содержать данные конкретного сервера, которые schema не распознаёт как server ID: URL, имена хостов в шаблонах `ds.N.hosts.M`, ID внешних модулей, ссылки на другие виджеты. Формат их не обезличивает; защитой при экспорте служит сканер экспорта P1-07C, а не schema.
- Неизвестный kind проекта, несовпадающий kind/root, target-поле и неизвестное структурное поле отклоняются благодаря закрытой schema/Rust-модели. Неизвестные данные виджета допускаются только внутри явно маркированного общего вида.
- V1 → v2: вызывающий код обязан выбрать Dashboard либо Page. Неоднозначное автоматическое сокращение нескольких dashboards/pages запрещено.

## Семантические ограничения

- Внутри проекта уникальны `catalog_id`, логические dashboard/page/widget ID; в каталоге уникален `metric_id`.
- В одном deployment **глобально уникальные** `slot_id`. Ссылки overrides только на существующие слоты/метрики. Одиночный виджет из `many` выбирается через объявленный `slot`, а не через первый элемент списка.
- `DeploymentState` не может содержать несопоставленные логические объекты, повторяющиеся Zabbix IDs и неопределённые результаты записи.
- `source.export_format_version` и `source.source_server_version` различаются. Исходные файлы с legacy `zabbix_version` принимаются только при чтении, новые файлы его не записывают.
- `value_type: binary` разрешён в каталоге, но запрещён для Graph и Item value в MVP; пользователь видит причину.
- Преобразование цветов в API Zabbix принадлежит виджет-кодеку версии, а не данным проекта.

## Пределы, происхождение и обмен с ИИ

Legacy `project/v1` не кодирует утверждённый UI scope `dashboard|page`; `project/v2` кодирует его полями `kind` и `root`. Ни один переносимый формат не кодирует publish intent и не доказывает доступность конкретных item/LLD-экземпляров или корректность отображения на любом сервере. Типы и размеры проверяются повторно после назначения узлов сети, до запроса API. ZIP не считается обезличенным: передача за периметр подчиняется политике организации и требует отдельного утверждения. Сами исходные экспорты шаблонов **не копируются** в переносимый пакет.
