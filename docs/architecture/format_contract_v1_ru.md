# Контракт файлов v1 (редакция v0.6)

Источники: `schemas/*.schema.json` (структура), ADR-012 (семантика), эталонный валидатор и тесты (примеры). «v1» описывает **наш формат**, а не поколение Zabbix. Расширения в v1 только обратно совместимые; несовместимые изменения требуют `/v2` и явной миграции.

> **O-025/O-026:** UI оперирует локальным черновиком одной панели либо одной страницы (инженерное имя — typed Dashboard/Page project; в интерфейсе слово «проект» и имя формата не показываются). Текущий `zdashstitch.project/v1` допускает 1–16 `dashboards[]` и не хранит этот scope, поэтому ниже он описан как существующий legacy exchange container, а не как окончательный UI domain contract. Схема, fixtures и код не меняются до отдельного решения о versioned representation и migration path. См. [`domain_model_v1_ru.md`](domain_model_v1_ru.md).

| Файл/ресурс | Формат | Переносится | Создаётся когда |
|---|---|---|---|
| `project.yaml` | `zdashstitch.project/v1` | Да | Legacy DATA-ONLY container; в архиве фиксированное имя |
| `metrics/*.yaml` | `zdashstitch.metrics/v1` | Да, после классификации | Импорт и нормализация шаблонов |
| `bindings.local.yaml` | `zdashstitch.local-bindings/v1` | **Нет** | В закрытом контуре после выбора hostid |
| `deployment.local.yaml` | `zdashstitch.deployment-state/v1` | **Нет** | После проверенной публикации и повторного чтения |
| API snapshot, рабочая копия импортированной панели, журнал операций | Внутренние `zdashstitch.raw-snapshot/v0`, `zdashstitch.workcopy/v0`, `zdashstitch.journal/v0` в каталоге данных пользователя (ADR-012 D-11) | **Нет** | Импорт с сервера, локальные изменения импортированной панели, каждая попытка публикации |

## Контейнер передачи

Один ZIP с `project.yaml` и **ровно** перечисленными в `catalogs[].file` файлами из `metrics/`. Запрещены внешние ссылки, каталоги вложений, CSS/JS, лишние файлы и относительные выходы из области пакета. ZIP не должен содержать `bindings.local.yaml` даже при экспорте из уже связанного проекта. Образцы: `examples/db-pilot.yaml` и `examples/db-pilot-package.zip`. Последний — **синтетический**, не документ Zabbix.

## Семантические ограничения

- Внутри проекта уникальны `catalog_id`, логические dashboard/page/widget ID; в каталоге уникален `metric_id`.
- В одном deployment **глобально уникальные** `slot_id`. Ссылки overrides только на существующие слоты/метрики. Одиночный виджет из `many` выбирается через объявленный `slot`, а не через первый элемент списка.
- `DeploymentState` не может содержать несопоставленные логические объекты, повторяющиеся Zabbix IDs и неопределённые результаты записи.
- `source.export_format_version` и `source.source_server_version` различаются. Исходные файлы с legacy `zabbix_version` принимаются только при чтении, новые файлы его не записывают.
- `value_type: binary` разрешён в каталоге, но запрещён для Graph и Item value в MVP; пользователь видит причину.
- Преобразование цветов в API Zabbix принадлежит виджет-кодеку версии, а не данным проекта.

## Пределы, происхождение и обмен с ИИ

Статический container сохраняет логическое содержимое, но в v1 не кодирует утверждённый UI scope `dashboard|page` и publish intent. Он не доказывает доступность конкретных itemid/LLD-экземпляров или корректность отображения на любом сервере. Типы/размеры проверяются повторно после назначения хостов, до запроса API. ZIP не считается обезличенным: передача за периметр подчиняется политике организации и требует отдельного утверждения. Сами исходные экспорты шаблонов **не копируются** в переносимый пакет.
