# Правила ведения документации и статусов

**Назначение:** не дать агенту принять пожелания за реализованные функции или устаревший аудит за действующий контракт.

## Приоритеты при расхождении

1. **Проверенные свойства реально установленного Zabbix**, подтверждённые лабораторными контрактами: определяют, что физически возможно (не разрешают самовольное изменение проекта).
2. **Схемы/инварианты** `schemas/` + нормативные ADR в порядке уточнений (ADR-012 корректирует ADR-001—011; ADR-013 фиксирует лицензирование; последующие принятые ADR — только явно).
3. Контракты `docs/architecture/*`.
4. Корневые README как публичные границы MVP и критерии пользовательского результата.
5. `ROADMAP.md` / `ROADMAP.ru.md` как направления после MVP; локальный `TASKS_RU.md` хранит состояние исполнения, но не вправе менять публичный контракт.
6. История Git и игнорируемый локальный `docs/history/`, если он существует, — **только история** и при несовпадении никогда не нормативны.

Если нормативные документы противоречат друг другу, нужно создать запись в `OPEN_DECISIONS.md` и остановить спорную операцию до согласования; не делать скрытый выбор.

## Статусы

- `planned` — требование/задача описано, реализация не подтверждена.
- `partial` — часть реализована, приёмка не пройдена.
- `blocked` — дальнейший прогресс требует испытания, доступа или решения.
- `verified` — критерии приёмки фактически пройдены, есть доказательства.

Не смешивать версии **архитектурного документа** (v0.6) с номером **приложения** (MVP 0.1.0). Количество успешно пройденных Python-тестов фиксируется в конкретном отчёте и относится только к эталонной проверке форматов.

## Поддержание единого набора

При изменении схемы: исправить генератор `tools/build_schemas.py`, воспроизвести схемы, негативные тесты, примеры, контракт и связанные ADR, описать совместимость со старыми файлами. При изменении MVP: согласовать и синхронно исправить README, ADR/контракты и локальный план. При изменении post-MVP направления — обновить обе языковые версии корневой дорожной карты. После этапа: добавить реальное состояние и доказательства в журнал. Никаких обещаний готовности без установленного артефакта и испытаний.
