# ADR-011 — многоверсионная архитектура и контракты совместимости

**Редакция:** v0.5, 2026-10-23. **Статус:** принято как архитектурный принцип; адаптеры кроме 7.4 не реализованы, узкая запись `itemid` на 7.4.16 испытана в P0, остальные операции требуют собственных контрактов.

## Мотивировка

Первый выпуск решает задачи на Zabbix 7.4, но в будущем потребуются 7.0 LTS, 6.0 LTS, 8.0, возможно 5.4 и 5.0. API изменяет модель панелей и наборы полей виджетов: в 5.0 у глобальной панели есть `widgets` непосредственно, а начиная с 5.4 — `pages`; наборы виджетов и их полей меняются от релиза к релизу. Поддержку конкретной операции доказывают контрактные испытания, не номер версии сам по себе.

**Правило:** UI, PortableProject, MetricCatalog, логические роли, каталог файлов, механизмы планирования и журнал **не зависят** от версии сервера. Весь перевод в Zabbix и обратно ограничен адаптерами. «Поддерживается 7.4» не означает «примем и запишем в 7.0/8.0 без проверки».

## Решение 1 — два независимых направления преобразования

```text
Export YAML/JSON/XML (разные версии)
    → ExportFormatDetector → VersionedExportParser → NormalizedMetricCatalog
                                                ↓
PortableProject/v1 ← OfflineEditor → Core logical models → Intent/PublishPlan
                                                ↓
                                       Target Adapter Registry
                                        /       |        \
                               Zabbix 5.x   6.x/7.x    8.x+
                                            (в MVP реализуем только 7.4)
                                                ↓
                                    API payload и проверка результата
```

Различаем **версию экспортированного шаблона** и **версию целевого сервера**: они могут не совпадать. Никакого обязательного требования `source.zabbix_version == server.version`. Проверяется совместимость метрик, виджетов и операций, а не совпадение цифр.

## Решение 2 — версии в данных

- `project.format = zdashstitch.project/v1` — версия **нашей схемы**, а не Zabbix. Никакого `zabbix_version: 7.4` в PortableProject как обязательного требования.
- `metrics.format = zdashstitch.metrics/v1` — версия **нашего каталога**. `source.export_format_version` — версия файлового `zabbix_export.version`; `source.source_server_version` — версия API исходного сервера; для `manual` версия не требуется. Устаревшее `source.zabbix_version` из v0.5 принимается при чтении, но **не записывается** в новые файлы. Версия формата не подтверждает поддержку парсером и не является условием допуска к записи.
- `RawDashboardSnapshot` всегда содержит точную версию ответа (`server_version`, идентификатор адаптера, fingerprint). Это не переносимый объект и не payload для записи в другой сервер.
- `LocalBindings/DeploymentRecord` дополнительно связываются с `connection_id`, версией цели при последнем разрешении и состоянием проверки; при изменении версии сервера перед записью пересчитываем возможности и ссылки.
- `PublishPlan` содержит целевую версию и идентификатор адаптера, скопировавшие план на другую версию или при обновлении целевого сервера, план инвалидируем.
- Новые типы виджетов или шаблонные панели, не предусмотренные проектом v1, добавляются **явным расширением схемы** (`project/v2` или согласованная эволюция), а не молчаливым включением неизвестных полей. Открытие новых схем старым приложением — понятная ошибка с предложением обновиться; запрет тихой потери данных.

## Решение 3 — адаптер и возможности

Адаптер собирается из независимых обязанностей, не создаём `if version` в UI/ядре:

- `VersionDetector`: `apiinfo.version` до авторизации; сохраняет строку версии, семейство и признак prerelease. Не считать prerelease обычным поддерживаемым выпуском. Для неопознанной версии — отказ в записи.
- `AuthStrategy`: пользовательский сеанс и API-токен с учётом отличий транспорта и API. Не предполагать одинаковую схему `auth`/HTTP-заголовка для всех поколений.
- `DashboardReader`: нормализация **global** и позднее **template** dashboard. Для панелей 5.0 может построить *внутреннюю виртуальную страницу* при чтении; нельзя обещать обратную запись многосоставной панели как одной страницы без явной трансформации.
- `WidgetCodec`: чтение, определение ссылок и формирование полей по API-типу и версии; отдельные реализации `svggraph`, `graph`, `item`, новых типов. Не использовать единый "graph"-кодек для разных видов графиков.
- `SourceResolver`: разрешение логических ролей и метрик в действительные объекты конкретного сервера.
- `DashboardWriter`: генерирует допустимый запрос, обеспечивает тесты сохранности и постпроверку; только из `VerifiedPlan`.
- `ExportParser`: отдельно от сетевого адаптера; загрузка шаблона версии X должна работать без сервера версии X.

**Capabilities** описывают не только поддержку версии сервера, но и конкретные операции: `read_dashboard`, `create_global_dashboard`, `append_page`, `append_widgets`, `clone_dashboard`, `replace_host`, `create_widget`, `preserve_widget`, `write_template_dashboard`, `import_template_export` (последняя — отдельный профиль входного файла). Для `create_widget`/`replace_host` и `preserve_widget` обязательно учитывать тип виджета. Каждая возможность имеет состояния `verified`, `experimental`, `unsupported`, `unknown`, `not_applicable` и ссылки на контрактные тесты. Только **verified** допускает запись.

Нельзя объявлять целую ветку "поддерживаемой для записи" лишь потому, что один `dashboard.get` удачно сработал. Отчёт о совместимости формируется для **конкретного плана** (все страницы, типы виджетов, ссылки, нужные операции и права).

## Решение 4 — адаптеры и выбор реализации

- В MVP регистрируем только `Zabbix74Adapter`. Допуск определяется одновременно веткой `7.4.x`, профильной матрицей конкретной операции и необходимыми проверенными полями/возможностями. Сборка с новым patch не считается автоматически идентичной испытанной: действуют объявленные диапазоны и runtime-проверки; если доказательств недостаточно — read-only для этой операции. Не нужно вручную разрешать каждый патч, но и не надо автоматически разрешать все.
- В следующем этапе добавляем `Zabbix70Adapter`, `Zabbix60Adapter`, затем адаптер 8.0 после подтверждения стабильного выпуска; 5.4 и 5.0 — отдельные более ограниченные реализации. Общие компоненты переиспользуются **внутри адаптеров** через композицию, а не через цепочку наследования `5 -> 6 -> 7 -> 8`.
- Версию при подключении получаем через `apiinfo.version`; затем `AdapterRegistry` выбирает проверенную реализацию для семейства и набора известных сборок. Если её нет — объяснимый отказ в операциях записи; никакого тихого `fallback` на 7.4.
- При обновлении целевого Zabbix кеш capabilities, готовые планы и соответствия, требующие проверки, инвалидируются. Уже сохранённый переносимый проект остаётся читаемым.

## Решение 5 — ограничения переноса и сетки

- Проект v1 использует собственную **эталонную логическую сетку 72×64**: существующие схемы проверяют её границы. Это **не утверждение**, что любая версия Zabbix использует ровно такие же ограничения.
- Каждая целевая версия сообщает `LayoutConstraints`: размеры сетки, допустимые размеры, набор типов виджетов, ограничения на страницы/виджеты/ряды и дополнительные правила. Конкретные значения заполняем по документации и контрактным тестам.
- При несовместимости фиксированного макета **не меняем расположение молча**. В MVP блокируем запись. В будущем явная операция `ReflowForTarget` создаёт предпросмотр и требует подтверждения.
- Отсутствующая возможность (например, страницы в 5.0, новый виджет 8.0 или неизвестное поле) формирует `CapabilityIssue` и блокирует соответствующую операцию, не приводит к удалению неподдержанного.
- При клонировании существующей панели в том же сервере сохраняем сырые неизвестные поля только по правилам **этого же** адаптера; межверсионный перенос снимков допускается только через явную нормализацию или блокировку, но не пересылкой чужого JSON.

## Решение 6 — тесты расширений

Для каждого нового адаптера — отдельный набор версионированных fixture и испытаний:

1. Определение версии и невозможность записать через чужой адаптер.
2. Чтение глобальной панели, сохранение логических ID и исходных внешних ID в непереносимой части.
3. Повторное чтение, сравнение, сохранность прав и невовлечённых страниц/виджетов.
4. `svggraph`, `graph`, `item` и реальные типы версии; недоступные типы явно блокируются.
5. Таблица полей и межвиджетных `reference`; замена хостов без разрушения связанных элементов.
6. Преобразование шаблона версии X из YAML/JSON/XML в MetricCatalog без подключения к серверу; отсутствующие зависимости отмечены, а не угадываются.
7. Исходный шаблон версии X → проект v1 → целевой сервер версии Y: метрики и роли разрешаются заново, отсутствие возможности блокирует запись.
8. Прогон одного переносимого проекта на 7.4 и на новой версии: одинаковое намерение при различиях API, в пределах реальных поддерживаемых возможностей.
9. Негативные тесты на неизвестную сборку, prerelease, исчезнувшие поля, новый тип виджета, сменившуюся модель страниц, недостаток прав и изменённую после preview панель.

**Статус:** реализация 7.4 и P0 — задача сейчас. ADR-012 уточняет инварианты форматов, предикаты VerifiedPlan и патч-политику. Остальные адаптеры и их подтверждения **не считаются готовыми**.

## Файловая структура

```text
crates/
  core/                    # переносимые объекты, роли, проект, layout-v1
  template_import/
    common/                # нормализованный каталог
    zabbix_exports/        # распознавание формата и версии, versioned parsers
  zabbix/
    transport/             # JSON-RPC, TLS, общая обработка ошибок
    registry/              # VersionDetector, AdapterRegistry, Capabilities
    adapters/
      v7_4/                # ЕДИНСТВЕННЫЙ реализуемый в MVP
      # v7_0/, v6_0/, v8_0/, v5_4/, v5_0/ — позже, по результатам тестов
    widgets/               # совместимые внутренние помощники кодеков, не смешивать API-типы
  application/
    operations/ planner/ publishing/ bindings/ journal/
apps/local_server/         # Axum: только HTTP-оболочка
ui/                        # отображает capabilities, не содержит version switch
schemas/                   # версии нашего переносимого формата
```

## Критические запреты

1. Никаких проверок веток Zabbix во frontend, core и логике формирования намерений; разрешено только показывать сведения о совместимости, полученные из registry/application.
2. Никаких вызовов `dashboard.update/create` в UI, вне единого publisher или без проверенного контракта конкретного адаптера.
3. Никакого привязывания `project-v1` к `7.4` и никакой отправки API-объектов другого поколения.
4. Никакой автоматической обратной миграции/потери неподдержанных полей.
5. Никакого объявления планируемой поддержки версии проверенной поддержкой без контрактных испытаний.

## Источники для проверки

- Zabbix 5.0: `dashboard.create` — `widgets` без `pages`.
- Zabbix 5.4 / 6.0: `dashboard.create` — `pages`.
- Zabbix 7.4: `apiinfo.version`, API changelog 7.2→7.4, объекты панели.
- Zabbix 8.0 (на 23.10.2026 документация помечена devel): API changelog 7.4→8.0, не считать стабильной совместимостью.
