# ADR-006—010 — операции, компоновка, безопасность и испытания

**Дата:** 2026-10-23. **Дополнение:** ADR-011 определяет общий контракт совместимости версий. **Статус:** решения на уровне контрактов MVP; детали API-реализации проверяются в P0.

**Поправка O-025/O-026 от 24.10.2026:** операции ниже применяются к явным source/target и object scope. `CreateDashboard` получает Dashboard project/Workcopy; `AppendPage` — Page project/source Page и отдельно выбранный target Dashboard; `AppendWidgets` — Widgets selection и target Page. Старый `project/v1` не является основанием смешивать эти kinds.

## ADR-006. Жизненный цикл проекта и конкретные операции

Идентичности проектов/панелей/страниц/виджетов — стабильные логические ID; идентичности Zabbix живут отдельно в `DeploymentRecord` и `IdentityMap`.

| Намерение | Точное поведение | Запрещённое неявное поведение |
|---|---|---|
| `CreateDashboard` | Создать новую глобальную панель, по умолчанию **приватную**; пользователь подтверждает имя и страницы, может явно задать общий доступ (O-031) | Найти/перезаписать панель с похожим именем |
| `AppendPage` | В выбранную по `dashboardid` панель добавить конкретную новую страницу; существующие страницы не изменять | Объединять страницы по имени |
| `AppendWidgets` | На выбранную по `dashboard_pageid` страницу добавить конкретные новые виджеты, сохранив существующие | Удалить/переупорядочить старые виджеты |
| `CloneDashboard` | Копировать выбранную панель внутри **одного** подключения, предложить новое имя и сопоставление источников | Неявно переносить права, копировать сломанные ссылки |
| `ReplaceHost` | В указанной глобальной панели заменить ссылки старого `hostid` на источники нового в проверяемых виджетах | Подставлять IP как строку или без проверки менять все найденные имена |

**Повторное применение:** MVP не делает автоматический `Sync`. Каждая операция создаёт новый проверяемый план. Повторный `Append*` с тем же `project_id` и логическими ID в том же DeploymentRecord по умолчанию блокируется как потенциальный дубль. Если локальная запись утеряна, приложение не угадывает принадлежность виджета по названию: пользователь вручную выбирает операцию, а повторный импорт показывает риск дубликатов. Сопоставление widgetid после публикации строится только по реально подтверждённым API-данным; при неоднозначности помечается как неопределённое, а не выдумывается.

**Ссылки между виджетами:** парсер собирает определения и потребителей `reference`, проверяет уникальность в целевой области, строит таблицу преобразования при клонировании/добавлении, обнаруживает неизвестные внешние ссылки. Если безопасно переписать все ссылки нельзя, операция блокируется. Неизменённый виджет нельзя переиспользовать как «новый» с прежним `widgetid`.

**Объединение панели и YAML:** нет произвольного «слияния» или синхронизации. Выбирается одна из трёх явных целей `CreateDashboard / AppendPage / AppendWidgets`; никакого автоматического поиска целевой страницы по совпадению имени. `CloneDashboard` — отдельный сценарий из сырых данных API, не из абстрактного YAML.

## ADR-007. Развёртывание ролей и геометрия

В переносимом проекте v1 эталонные координаты задаются в клетках сетки 72×64, что соответствует Zabbix 7.4. При публикации адаптер каждой версии повторно проверяет её `LayoutConstraints`; никаких неявных преобразований. Размер каждого виджета задаётся числом клеток. `layout.mode=auto` означает, что в YAML сохранены только желаемые `w/h`, а точные `x/y` рассчитываются после назначения хостов. `layout.mode=fixed` задаёт x/y/w/h и проверяется на границы/пересечения.

- `series_per_host`: **один** график; для каждой записи `series` создаются ряды по выбранным слотам хостов. Разные записи могут ссылаться на разные каталоги и роли; смешанные единицы отображения требуют предупреждения и, если нельзя корректно настроить оси, отказа.
- `widget_per_host`: по одному Item value на слот выбранной роли. Слоты упорядочены локально; ключ экземпляра `(logical_widget_id, slot_id)`, а заголовок может выводить обозначение хоста в интерфейсе, но в переносимом YAML реальное имя не сохраняется.
- `single`: один Item value; `selection: one` требует роль `cardinality: one`, а роль `many` допускает **только** `selection: slot` с объявленным логическим `slot_id`. Нельзя молча брать первый хост.
- Развёртывание ролей производится **до** размещения. Пустая роль — нерешённая обязательная зависимость, а не ноль успешно созданных карточек. Предельное число виджетов и рядов задаёт дополнительный адаптер/ограничения конкретной версии.
- При `AppendWidgets` существующие координаты **никогда** автоматически не меняются. Добавляем в свободные клетки; если виджет не помещается, предлагаем новую страницу или отказ. При `CloneDashboard` сохраняем исходное расположение, изменяем его только по явному запросу.
- Автономный предпросмотр помечает переменное количество виджетов, если роль many ещё не привязана. Он не является снимком будущего интерфейса Zabbix 1:1.

## ADR-008. Авторизация, файлы и локальный HTTP

**Три режима:** автономно; API-токен; `user.login` с именем/паролем. Для учётных записей с MFA `user.login` Zabbix 7.4 не работает; предложить разрешённый администратором API-токен. Секрет Zabbix живёт **только в Rust** и отдельно от короткоживущего токена локальной сессии Axum. Пароль по умолчанию нигде не сохраняется; токен — в системном хранилище только по выбору пользователя, иначе в памяти. По возможности завершать `user.login`-сеанс через `user.logout`.

HTTP: слушать только loopback, использовать случайный свободный порт, собственную случайную локальную сессию, проверку `Host`, `Origin`, защиту CSRF для операций изменения, CSP, отсутствие открытого CORS, HTML escaping пользовательских текстов. Никакого удалённого bind по умолчанию, никакого «перехода в серверный режим» переключателем без самостоятельного пересмотра модели безопасности. TLS до Zabbix проверяется, самоподписанный корень подключается явно; глобальное отключение проверки TLS не поддерживать по умолчанию.

**Уточнение O-017 (2026-10-24):** браузер получает локальную сессию только через одноразовый bootstrap-код. Лаунчер открывает `http://127.0.0.1:<port>/?bootstrap=<code>`; код случайный (не короче 128 бит), одноразовый и короткоживущий. Сервер обменивает его на cookie `HttpOnly; SameSite=Strict; Path=/` и перенаправляет на `/`, убирая код из адресной строки. Каждый `/api`-запрос требует cookie и проверенные `Host`/`Origin`; изменяющий запрос дополнительно несёт CSRF-токен в заголовке. Сессия живёт до завершения процесса; повторный запуск при работающем процессе выдаёт новый bootstrap-код через механизм единственного экземпляра.

Парсеры файлов: размер файла/глубина/количество объектов ограничены; дубли ключей YAML отклоняются; aliases отключены в нашем первичном валидаторе; XML — без XXE, внешних сущностей или сетевой загрузки; ZIP пока не поддерживается; локальные ссылки на каталоги не могут уходить за пределы каталога проекта или быть symlink. После парсинга строгая schema+semantic validation, строковые поля в UI трактуются как текст, а не HTML/скрипт. Неизвестные поля в переносимом v1 — ошибка, а не игнорирование.

**Конфиденциальность:** `Save portable project` сохраняет модель без локальных Zabbix bindings, но не гарантирует отсутствия чувствительных имён/ключей, введённых человеком. Внешний экспорт (`ApprovedExternalExport`) — отдельный будущий сценарий с allowlist, проверкой и подтверждением. В MVP пользователю явно предупреждаем, что переносимый файл нельзя считать автоматически разрешённым к передаче за пределы компании.

## ADR-009. План, частичная ошибка и результат публикации

Состояния локальной операции: `draft` → `validated` → `confirmed` → `writing` → одно из `structurally_verified`, `partial_failure`, `unknown_outcome`, `failed_before_write`. Нельзя путать факт HTTP 200 с успехом: нужно проверить JSON-RPC error и фактическую конфигурацию повторным чтением.

План содержит fingerprint канонизированных исходных страниц/полей, выбранные конкретные источники, права, разрешённые преобразования, диагностические причины и конкретную ожидаемую конфигурацию. До записи повторное чтение и recheck целевых объектов. Нет CAS и общей транзакции над несколькими панелями. Неизвестный исход (`unknown_outcome`) — без слепого повтора; reconciliation чтением, затем новый план. Писать журнал **без паролей, токенов, потенциально секретных свободных строк**; для сырого снимка обеспечить локальные права доступа и отдельную политику хранения.

После исполнения результат маркируется тремя независимыми проверками:
- `structurally_verified` — API содержит ожидаемые страницы/виджеты/поля и не показывает потери незатронутого;
- `data_source_verified` — целевые host/item/graph существуют и соответствуют проверенным ссылкам;
- `visually_unverified` — реальное отображение не подтверждено человеком в Zabbix; кнопка открыть опубликованную панель.

Сохранённый снимок **не гарантирует** полное восстановление: ссылки на удалённые объекты могут быть невосстановимы. Автоматический rollback после сетевой ошибки не выполнять до установления фактического состояния.

## ADR-010. Контрактные испытания P0 и критерий разрешения записи

**Прежде чем обновлять существующую продуктивную панель, на лабораторной установке той же ветки 7.4 выполнить:**

1. Read → snapshot → сохранение без записи; проверить `selectPages`, `selectUsers`, `selectUserGroups`, сохранность строковых ID и полей.
2. Update одной страницы при нескольких: остальные страницы остаются и сохраняют порядок.
3. Update одного `item` с полным fields: соседние десять виджетов не меняются.
4. Тест неизменённого неизвестного виджета: допустимо ли сохранить по `widgetid` без повторной передачи его `fields`.
5. Тест `svggraph` с несколькими хостами, масками и overrides; редактировать лишь проверяемое подмножество.
6. `graph` classic и графики с `graphid`: отдельная проверка полей и принадлежности метрик.
7. Копирование панели с ссылками selector/reference; проверка сохранности потребителей и отсутствия конфликтов.
8. Панель меняется вторым администратором после preview: публикация блокируется.
9. Сетевой обрыв после отправки: повторное чтение, никакого слепого retry.
10. Копирование с исходной публичной панелью: новая приватна, если доступ не копировали; копия доступа (O-031) переносит только видимые учётной записи записи и проверяется повторным чтением.
11. Отсутствие прав на часть элементов: неопределённость не классифицируется уверенным `missing`.
12. Автономные проверки YAML/JSON/XML и смешанных каталогов, а также Windows 10/Linux packaging.

**Матрица возможностей** хранится в реестре адаптера выбранной версии (ADR-011) по типу виджета и действию (`inspect`, `create`, `clone`, `replace_host`, `append`, `preserve_unmodified`) и сопровождается fixture/test ID. Если операция не покрыта тестом для 7.4 — кнопка публикации для соответствующего сценария блокируется. Нельзя маркировать проверку пройденной только по исходному коду Zabbix или по валидности JSON Schema.

## Дополнение v0.5 к ADR-010

Для всех новых версий требуются собственные fixtures и контрактные тесты чтения/записи; существование теста Zabbix 7.4 не подтверждает работу того же сценария на 7.0, 6.0, 8.0 или 5.x. Неподдержанная версия допускает автономную работу и безопасную диагностику, но не публикацию.

## Дополнение v0.6

- Минимальный переносимый артефакт MVP — DATA-ONLY ZIP с `project.yaml` и указанными `metrics/*.yaml` либо локальная папка этих файлов. Ресурсы, JS/CSS, снимки Zabbix и локальные привязки не включаются. Это не механизм автоматического допуска к передаче внешнему ИИ. Подробнее ADR-012.
- Безопасный импорт: Python-прототип запрещает символические ссылки (POSIX через `O_NOFOLLOW` и открытие сегментов пути), ZIP обрабатывает в памяти без распаковки. Реализация Rust на Windows отдельно запрещает reparse points.
- При вводе токена или пароля через Svelte секрет **временно существует в браузере и loopback-трафике**. Нельзя утверждать «секрет никогда не попадает в браузер». Запрещены сохранение в localStorage/URL/log, внешние запросы, доступ стороннего содержимого. Для политик, полностью запрещающих ввод через браузер, позднее потребуется нативный диалог.
- Журнал операций со статусом `unknown_outcome` отдельный от `deployment-state`, который хранит **только подтверждённые** публикации.
