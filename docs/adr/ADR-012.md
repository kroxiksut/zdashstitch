# ADR-012 — устранение замечаний к v0.5: данные, перенос, разрешение, безопасность

**Дата:** 2026-10-23. **Статус:** принято как **проектный контракт v0.6**, не как подтверждение поведения API Zabbix. **Нормативность:** этот ADR уточняет и в случае расхождения заменяет соответствующие положения ADR-001—011. Для структуры данных первичны `schemas/*.schema.json`; для межфайловых инвариантов — разделы ниже и контрольные фикстуры. Поддержка Zabbix 7.4 должна быть отдельно подтверждена P0.

## D-01. Четыре независимых класса данных

1. `PortableProject`: `zdashstitch.project/v1`, логические панели, страницы, виджеты, группы/роли, `slot_id`, ссылки на каталоги. Не содержит `hostid/itemid/widgetid` и строк адресов как привязок. **Может** содержать чувствительные значения в свободном тексте; это не очищенный внешний экспорт.
2. `MetricCatalog`: `zdashstitch.metrics/v1`, один нормализованный исходный шаблон/каталог, метрики, типы, ключи или псевдонимы. `binary` допустим как метаданные, но недопустим для графика и в MVP для `item_value`.
3. `LocalBindings`: `zdashstitch.local-bindings/v1`, `project_id`, `connection_id`, `deployment_id`, роли со слотами и реальными `hostid`, индивидуальные подтверждённые соответствия метрик. Локальный приватный объект; не упаковывать в переносимый ZIP.
4. `DeploymentState`: `zdashstitch.deployment-state/v1`, **только подтверждённая последним повторным чтением** идентичность реальных dashboard/page/widget, adapter/server version, fingerprint. Локальный приватный объект. История операций и `unknown_outcome` — **отдельный журнал**, никогда не представлять неопределённый результат как подтверждённый deployment.

Стабильная идентичность повторяемого виджета: `(logical_dashboard_id, logical_page_id, logical_widget_id, logical_slot_id?)` в рамках deployment. `slot_id` уникален для всех ролей одного deployment, даже если логически разные роли могли бы иметь одинаковые названия. `widgetid`, `reference`, логический ID и `slot_id` не взаимозаменяемы. Любое сопоставление ID после публикации строится по фактическому ответу Zabbix и проверке; при неоднозначности не выдумываем запись в `DeploymentState`.

`connection_id` фиксирует выбранный профиль; изменение URL/идентичности целевого сервера в том же профиле требует инвалидировать подготовленные планы и подтвердить принадлежность опубликованных ID новому серверу. Для полной защиты необходим также fingerprint контекста целевого подключения, определяемый безопасным локальным способом, без помещения ключей или токенов в журнал.

## D-02. Источник и версия формата — разные вещи

В `MetricCatalog.source`:

| `kind` | Новые поля | Значение |
|---|---|---|
| `template_export` | `export_format_version` (обязательно), `source_server_version` (необязательно, если достоверно известно) | Значение `zabbix_export.version` из исходного файла — версия **формата** |
| `zabbix_api` | `source_server_version` (обязательно) | Версия API исходного сервера при чтении |
| `manual` | Никакой версии не требуется | Создано вручную/ИИ; версия сервера неизвестна |

`source.zabbix_version` из v0.5 допустимо **только при чтении старых файлов**. При импорте для `template_export` значение становится `export_format_version`, для `zabbix_api` — `source_server_version`; для `manual` оно игнорируется. Новые файлы записываются без `zabbix_version`. Строка вроде `8.0.0alpha1` допускается как метаданные, но не подтверждает поддержку парсера или запись в prerelease.

`target_server_version` не помещается в проект и каталог: оно существует только в состоянии целевого подключения/снимка/публикации.

## D-03. Правило нормализации файлов экспорта с несколькими шаблонами

`template_import` принимает **один файл** с N шаблонами и выдаёт **N отдельных каталогов**, не N копий исходного файла. Один каталог = один шаблон-источник; создаётся детерминированный локальный `catalog_id` (при коллизии имён — дополнительный стабильный суффикс от UUID или хеша данных), а также таблица соответствия «оригинальная ссылка → catalog_id/metric_id».

- В метрики каталога попадают только разрешённые поля нормализации; исходные макросы, скрипты, пароли, SQL, URL, параметры подключения не копируются как есть.
- Связи шаблонов сохраняются как диагностика зависимостей; непосредственно унаследованные элементы не выдумываются. Если родитель отсутствует, частично доступны только метрики, которые действительно присутствуют в исходном экспорте.
- UUID повышает уверенность, но не заменяет разрешение фактических `itemid` на целевом хосте. LLD-прототип не считается экземпляром элемента данных.
- Дубли/неоднозначности имён, ключей и UUID проверяются отдельно; не сливать показатели по совпавшему имени.
- **Реальный parser YAML/JSON/XML 7.4 ещё не реализован**. Текущие схемы и тесты проверяют нормализованный результат, а не доказывают корректный импорт всех экспортов.

## D-04. Минимальный самодостаточный переносимый пакет MVP

Обычный локальный проект может храниться как папка с `db-pilot.yaml` и `metrics/*.yaml`. **Пакет обмена v1** — ZIP только из `project.yaml` и каталогов `metrics/<id>.yaml`, точно перечисленных в проекте. Никаких `LocalBindings`, `DeploymentState`, журналов, API-снимков, кэша, произвольных ресурсов, JS/PHP/CSS, исполняемых файлов, сетевой загрузки и скриптов при импорте.

- Архив проверяется **без распаковки на файловую систему**; пути нормализуются и проверяются по белому списку, дубликаты имён запрещены, ссылки и reparse-point записи запрещены, размер/количество/глубина/тип записей ограничены, чтение ограничено заранее известными размерами; содержимое валидируется как YAML с JSON Schema + межфайловыми правилами.
- Эталонные пределы текущего прототипа: ≤33 записей, ≤2 MiB на запись, ≤32 MiB суммарно, ограничение степени сжатия 300:1. Для приложения Rust пределы могут корректироваться только совместно со схемой и тестами. Это защитные лимиты, не гарантии от всех видов атак на парсер.
- Никакой сети или выполнения кода при импортировании.
- Даже пакет по белому списку **не разрешён автоматически к отправке внешнему ИИ**: значения полей `name`, `key`, `description` могут выдавать внутренние данные. Три раздельных действия: «сохранить локально», «перенести в разрешённом контуре», «подготовить для внешнего обмена» (последнее — **после MVP**, с проверкой по политике организации).
- Программа не должна автоматически собирать ZIP, включив в него всё содержимое рабочей папки. Экспорт — только через новое построение архива из перечисленных разрешённых файлов.

## D-05. Выбор источника из группы и повторение виджетов

`roles.<role>.cardinality`: `one` либо `many`. Для роли `many` могут быть объявлены переносимые логические слоты `slots: [keeper_a, keeper_b]`; реальные hostid остаются локальными. `selection` имеет три режима:

- `all`: все явно назначенные слоты, упорядоченно, **без** автоматического включения случайно появившихся хостов.
- `one`: только роль с `cardinality: one`; не выбирать первый хост из роли many.
- `slot`: только объявленный логический `slot_id` внутри роли (возможен `many`). Если слот не назначен локально, публикация блокируется.

`series_per_host` — одна графическая карточка; число рядов рассчитывается **после привязки**. `widget_per_host` — карточка на каждый слот; идентичность экземпляра основана на `slot_id`, а не hostid. `single` с `all` допускается лишь для `cardinality: one`. Роль без хостов — блокер.

Расширение выполняется до создания запроса и перед размещением. Из адаптера передаются `LayoutConstraints`, в том числе максимальное число рядов, виджетов, размеры и геометрия. Недопустимые результаты: `too_many_items`, `too_many_widgets`, `no_layout_space`, `unresolved_slot`, `unresolved_role`, `fixed_repeat_ambiguous`. Никакого тихого разбиения по дополнительным страницам, изменения размеров или удаления рядов. Для повторяемой карточки с `fixed` и более чем одним хостом — отказ до явного изменения схемы макета.

## D-06. Две независимые оси разрешения метрики

Запрещено использовать один enum, где `disabled` и `resolved_manual` взаимоисключают друг друга. `ResolutionOutcome` содержит:

- `match_status`: `confirmed_binding`, `unique_compatible`, `candidate_requires_confirmation`, `ambiguous`, `missing`, `not_visible_or_unknown`, `unresolved_lld`, `unsupported`.
- `usability`: `usable`, `disabled`, `unsupported_state`, `incompatible_type`, `unknown`.
- `diagnostics`: список причин и обоснований, в том числе `source_key_match`, `unit_mismatch`, `macro_unresolved`, `lld_instance_missing`, `dependency_unknown`.
- `requires_action`, `blocking`: отдельные вычисленные булевы свойства (на основании всех осей, матрицы возможностей и прав), а не попытка вывести безопасность только из `match_status`.

Случаи «элемент найден, но выключен» и «ручное соответствие есть, но изменилась единица измерения» должны отражаться полностью. Недоступность из-за прав не объявляется `missing` без достаточных оснований.

## D-07. VerifiedPlan — закрытая граница записи

В Rust `VerifiedPlan` может создать **только** доверенный планировщик, после всех проверок. Поля конструктора непубличны, тип не десериализуется из HTTP/YAML, UI видит opaque `plan_id`, а не исполняемый API-payload.

Минимальные предусловия плана: `operation`, `connection_id`, fingerprint идентичности цели, точная версия сервера, ID адаптера + версия/хеш capabilities, исходный `RawDashboardSnapshot` fingerprint, выбранный dashboard/page, разрешённые зависимости на реальные host/item/graph, актуальный набор полей виджетов, права пользователя, набор **проверенных** `CapabilityCheck` по всем вовлечённым типам/полям/ссылкам, время построения и признак одноразовости. UI подтверждает план, после чего приложение повторно читает и сверяет все существенные условия и собирает payload.

Статус capabilities `verified` — **результат контрактного теста** указанной операции/виджета/поля/ссылок для объявленного диапазона целевой версии; отсутствие нужного подтверждения запрещает запись. Отдельно оцениваются runtime-права и наличие/состояние метрик. Не вводить один глобальный флаг `is_supported` для всей версии.

Журнал операций использует состояния `planned → previewed → confirmed → submitting → verified` и варианты `failed_before_send`, `failed_after_response`, `unknown_outcome`, `reconciled_verified`, `reconciled_failed`. Финальный `DeploymentState` обновляется только после `verified`/`reconciled_verified` и повторного чтения; повторный запрос к API при `unknown_outcome` запрещён до выяснения фактического состояния.

При сетевой ошибке после отправки в Zabbix — `unknown_outcome`: никаких слепых повторных записей, сначала reconcilliation чтением. Только проверенные результаты попадают в `DeploymentState` (неизвестные — в журнал). Конфликт ручных изменений после preview блокирует применение или требует нового плана. Проверка перед записью уменьшает, но не устраняет гонку между чтением и обновлением; атомарного CAS API не обещаем.

## D-08. Версии и исправления

`AdapterRegistry` сопоставляет не просто 7.4 по цифрам, а точную целевую ветку, профиль возможностей и подтверждённые диапазоны исправлений. Разрешение по версии **само по себе недостаточно**. При патч-обновлении внутри ветки допустимость зависит от объявленной политики совместимости и runtime-проверок нужных особенностей. Не требовать вручную каждого patch для общих безопасных возможностей, но и не делать безусловный допуск на всю ветку. Для чужой minor/major, prerelease и непроверенной комбинации — без записи. Все новые адаптеры обязаны иметь собственные контрактные тесты.

## D-09. Граница секретов и локального браузера

В режиме токена либо логина/пароля секрет вводится в Svelte, кратковременно существует в JS и передаётся по локальному HTTP (даже если не используется внешний интернет). Запрещены localStorage, sessionStorage, URL, логи, аналитика, внешние ресурсы, отображение в диагностике. Токен Zabbix должен жить в Rust с минимальным временем хранения. Случайный session secret/CSRF-гарантии, проверки `Origin`/`Host`, привязка только к loopback, проверка обращения к локальному API — обязательны; только `127.0.0.1` недостаточно.

В первый выпуск браузерный режим **не является** секретонезависимым интерфейсом. Нативный ввод возможен позже для компаний с более строгими требованиями. TLS к корпоративному Zabbix: системные/настроенные доверенные центры, нельзя отключать проверку сертификата по умолчанию.

## D-10. Источник схем, проверок и эталонных фикстур

`tools/build_schemas.py` — **единственный генератор четырёх JSON Schema**; файлы в `schemas/` проверяются на воспроизводимость в CI. JSON Schema проверяет структуру, но не может обеспечить все ограничения связей/уникальности; `tools/validate.py` и `tools/preflight.py` содержат тестируемую Python-**эталонную реализацию** семантических правил. Для Rust обязательна эквивалентная реализация с теми же положительными/отрицательными fixtures; Python не является движком будущего продукта.

Набор проверок должен включать дубли `slot_id`, несоответствие catalog/metric/role, сломанные ссылки `DeploymentState`, тип `binary`, ручной каталог без версии, символические ссылки/архивы с traversal, нетипичные версии экспорта, переполнение рядов, виджетов и сетки, цвет `#RRGGBB` → `RRGGBB` в **версионном виджет-кодеке** (визуальная модель хранит `#`).

**Статус выполнения на 23.10.2026:** формальные схемы, Python-эталон и тесты данных реализованы в комплекте v0.6. Rust-адаптер 7.4, read-only transport, лабораторные контракты `dashboard.update` и закрытый `VerifiedPlan` publisher реализованы для узкой операции замены `itemid` в `item`-виджете на точно проверенной Zabbix 7.4.16. Остальные операции, виджеты и патчи не получают допуск автоматически; пользовательская HTTP/UI-публикация отсутствует. Python-тесты сами по себе по-прежнему не являются допуском к записи.
