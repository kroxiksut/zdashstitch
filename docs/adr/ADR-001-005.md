# ADR-001—005 — согласованная редакция с уточнениями v0.6

**Дата:** 2026-10-23. **Дополнение:** ADR-011 определяет поддержку версий Zabbix. **Статус:** правила модели приняты для проектирования; поведение записи и копирования **не подтверждено на живой установке** (см. ADR-010). Устаревшие версии доступны в истории Git.

**Поправка O-025/O-026 от 24.10.2026:** серверная и UI-иерархия — `Dashboard → Page → Widget`; локальный черновик имеет root kind Dashboard либо Page (инженерное имя до O-026 — Dashboard/Page project; в интерфейсе слово «проект» не используется, термины — по официальной русской локализации Zabbix). Термин `PortableProject/project-v1` ниже обозначает существующий legacy multi-dashboard exchange container до решения O-026, а не generic workspace и не окончательный typed-project contract. При конфликте действует `docs/architecture/domain_model_v1_ru.md` и более поздний ADR-012.

## ADR-001. Сущности, идентичности, данные с разными правами обращения

**Решение.** Пять базовых типов данных:

1. `PortableProject` — существующий legacy container `zdashstitch.project/v1`: глобальные Dashboards, Pages, логические Widgets, роли, ссылки на каталоги, размеры/расположение. Может существовать без сети и без хостов, но не хранит утверждённый root kind `dashboard|page`; typed replacement/migration решает O-026.
2. `MetricCatalog` — нормализованный список метрик шаблона `zdashstitch.metrics/v1`, независимо от того, получен из файла или API. Ссылка задаётся парой `(catalog_id, metric_id)`, не только именем шаблона.
3. `LocalBindings` (`schemas/local-bindings-v1.schema.json`, только внутреннее хранилище) — локальные привязки ролей к **упорядоченным слотам** (`slot_id` → `hostid`, `connection_id`), а также подтверждённые соответствия метрик. Секреты отделяются от обычного YAML проекта.
4. `RawDashboardSnapshot` — ответ Zabbix API в виде, сохраняющем неизвестные поля, версия сервера, время и контрольная сумма канонического представления. Это не восстанавливаемая полная копия Zabbix и не допустимый вход в `dashboard.update` без преобразования.
5. `PublishPlan` + `OperationJournal` — локальные одноразовые подготовленные действия, их предусловия, ожидаемые эффекты, фактическая история и состояния ошибок. Не являются переносимыми.

`DeploymentRecord` оформлен как локальный `zdashstitch.deployment-state/v1` (ADR-012) и связывает `(project_id, logical_dashboard_id, target_connection, zone)` с опубликованной `dashboardid` и проверенными сопоставлениями. MVP хранит минимальный журнал/связь; автоматическая двусторонняя синхронизация остаётся на будущее.

**Три уровня идентичности:** `logical_widget_id` из проекта; `widgetid` Zabbix из конкретной публикации; `reference` Zabbix, задающая связи между виджетами. Не смешивать. При `widget_per_host` стабильный локальный ключ экземпляра `(logical_widget_id, slot_id)`; не использовать `hostid` как переносимый ключ. Для Graph с N рядами логический экземпляр один, ряды определяются парой ссылки на ряд и слотом.

**Инварианты:** `hostid`, `itemid`, `graphid`, `dashboardid`, `widgetid` — строки только в адаптере Zabbix, снимках и локальных привязках; не преобразовывать в JS Number. Имя панели/страницы не является идентификатором. Проекту можно назначить несколько независимых DeploymentRecord без изменения исходного YAML.

## ADR-002. Границы кода и зависимостей

```text
crates/
  core/             # переносимые модели, роли, метрики, геометрия
  template_import/  # только локальный парсинг/нормализация Zabbix export
  zabbix/           # транспорт; registry/capabilities; адаптеры версий (реализуем v7_4), DTO, виджеты
  application/      # intents, bindings, matching, planner, publisher, journal
apps/local_server/  # Axum/loopback/security/session, выдача UI
ui/                 # Svelte + TypeScript, без секретов Zabbix
schemas/            # JSON Schema v1
```

`core` и `template_import` не содержат `ItemId`, `GraphId`, зависимостей от сетевых библиотек и знаний о формате запроса Zabbix. `zabbix` умеет прочитать/опознать API-ссылки и создать допустимый payload, но не решает за пользователя, можно ли принять несовпадающие метрики. `application` принимает намерения пользователя и единолично запускает запись только после проверенного плана. `local_server` не содержит алгоритмов редактирования виджетов. `ui` не отправляет запросы в Zabbix напрямую.

Публичные Rust-порты: `ProjectRepository`, `CatalogImporter`, `ZabbixReadGateway`, `ZabbixWriteGateway` (для него только разрешённый `VerifiedPlan`), `LocalBindingsStore`, `OperationJournal`. Зависимости application от адаптера идут через ограниченные интерфейсы, а не через произвольный raw JSON-RPC.

## ADR-003. Типизированная замена хостов и совместимость метрик

Операция `ReplaceHost` принимает **реальный** исходный и целевой `hostid` и область (в MVP — выбранная глобальная панель и её страницы). Адрес/IP не является идентичностью хоста; если адрес изменился при том же `hostid`, замена виджетов может не требоваться.

1. Считываем панель, нужные объекты `host.get`, `item.get`, `graph.get`, идентифицируем прямые и известные косвенные зависимости. Неизвестные зависимости фиксируются явно.
2. Ищем элементы данных целевого хоста по точному ключу `key_`, затем проверяем `value_type`, единицы, статус, происхождение, тип обнаружения; при необходимости `graph.get`. Предположение на основе похожего имени не считается совпадением.
3. Учитываем граф зависимостей «источник → виджет-получатель»: изменение селектора может косвенно изменить несколько карточек. Предпросмотр различает поля, которые изменяем, и отображение, которое может измениться.
4. Собираем локальный `ResolutionOutcome` с независимыми полями `match_status`, `usability`, `diagnostics`, `evidence`, `action_required`, `blocking_reason`. Ранее использовавшиеся значения `resolved_auto`, `disabled`, `missing` были смешением разных осей и **заменены** ADR-012. Историческая таблица ниже служит только для сопоставления старых терминов:

| Статус | Значение | Разрешает запись без действия пользователя? |
|---|---|---|
| `resolved_auto` | Однозначный совместимый кандидат по принятому правилу | Да, при остальных проверках |
| `resolved_manual` | Явно выбранный и подтверждённый кандидат | Да, после перепроверки |
| `needs_confirmation` | Есть кандидат с существенным расхождением | Нет |
| `ambiguous` | Несколько кандидатов | Нет |
| `missing` | Нужного элемента нет при достаточных правах/видимости | Нет |
| `not_visible_or_unknown` | Невозможно отличить отсутствие от ограничения доступа/сбоя | Нет |
| `disabled` | Элемент выключен | По умолчанию нет |
| `unsupported_state` | Элемент или прототип не поддерживается | Нет |
| `incompatible` | Противоречит требованиям отображения | Нет |
| `unresolved_lld` | Не выбран конкретный найденный экземпляр | Нет |
| `unsupported` | Неизвестное поле/ссылка/виджет | Нет для затронутого объекта |
| `unchanged` | Нет изменения | Не применимо |

Эта таблица — словарь v0.5, **не контракт v0.6**. Нормативный перечень — в ADR-012. Результат разрешения не означает наличия прав на запись. При отсутствии доступа к объекту статус нельзя выдавать как уверенное `missing`.

API-тип `svggraph` — современный Graph; `graph` — Graph (classic), отдельная схема и `graphid`; `item` — Item value. Для каждой операции существует таблица поддерживаемых возможностей адаптера (`inspect`, `create`, `clone`, `replace_host`, `append`, `preserve_unmodified`). В 0.1 гарантировать создание `svggraph` и `item` после контрактных тестов; остальные виды замены определяются инвентаризацией реальных рабочих панелей. Никакой «универсальной замены» неизвестных полей. **Решение O-003 (24.10.2026):** в MVP `replace_host` поддерживается для `item`, `svggraph` (явные items; строковый шаблон хоста — только при совпадении с видимым именем старого хоста без учёта регистра и без `*`, маски не меняются) и `graph` (classic: график с тем же именем из того же шаблона на целевом хосте, после лабораторного контракта). Остальные виджеты со ссылкой на старый хост не изменяются: план явно перечисляет их, и публикация требует подтверждения пользователя.

## ADR-004. Одно контролируемое место записи

**Путь:** `Read → Intent → Inspect/Resolve → BuildPlan → Validate → Preview → Confirm → Re-read → Compare + RecheckSource + Rights → WritePayloadBuilder → Write → Re-read → Verify → Journal`.

Ключевой контракт Zabbix 7.4: переданный `pages` в `dashboard.update` **заменяет состав страниц**; отсутствующие `dashboard_pageid` означают новую страницу, пропущенные старые страницы могут быть удалены. В режиме изменения страницы переданный `widgets` может изменить полный состав её виджетов. Поэтому мы **не отправляем** фрагмент страницы как «патч одного виджета».

`WritePayloadBuilder` составляет минимальный разрешённый запрос с сохранением всех существующих ID страниц, прав доступа и незатронутых объектов. Для нетронутых виджетов потенциально можно передавать только `widgetid` без `fields`, но эту семантику требуется подтвердить лабораторно. Если приходится менять `fields`, создаётся полный проверенный набор полей данного виджета; нельзя отправить только изменённое поле, потеряв остальные. `RawDashboardSnapshot` никогда не передаётся как payload напрямую.

Запретить прямой вызов `dashboard.update/create` из UI, `template_import` и произвольного application-хендлера. При обновлении контента не менять `private`, `userid`, `users`, `userGroups`; новую копию создавать **приватной по умолчанию**, перенос доступа — отдельный будущий сценарий.

`PublishPlan` одноразовый, содержит предикаты наличия/актуальности страниц, полей и источников. Перед записью перепроверяем не только fingerprint панели, но и целевые хосты/метрики/права. Встроенного CAS/транзакционного применения нескольких панелей нет; гонка между последним чтением и записью остаётся. При разрыве соединения после отправки: `unknown_outcome`, без автоматического повтора до reconciliation. После успешного API ответа различать структурную проверку, проверку источников и отсутствие доказательства визуального результата.

**Без живых P0-контрактов запись в существующую продуктивную панель запрещена.** Обещание гарантированного отката также запрещено: удалённые Zabbix-объекты могут сделать восстановление невозможным.

## ADR-005. Каталоги метрик, legacy project/v1 container и сопоставление

**Единственные форматы v1:** `zdashstitch.metrics/v1` и `zdashstitch.project/v1`, нормативные JSON Schema — `schemas/metrics-v1.schema.json` и `schemas/project-v1.schema.json`. Примеры прежних документов не являются спецификацией.

**MetricCatalog:** идентификатор, профиль экспорта, источник, диагностические причины неполноты, метрики с логическим ID, отображаемым именем, селектором (`key` либо `alias`), типом значения, единицами и `origin`. Список причин: `missing_parent_template`, `unresolved_macros`, `lld_requires_instance`, `source_partial`. Диагностики не блокируют *весь* каталог, только требуемые при публикации зависимости.

Экспортированный пользовательский шаблон может не содержать унаследованные и реально обнаруженные метрики: `template_import` их не выдумывает. Наличие LLD-прототипа не означает существование элемента данных; подключение к целевому серверу может быть обязательным для разрешения экземпляра. Источник метрики может быть `template_item`, `host_item`, `lld_prototype`, `discovered_item`.

**Происхождение каталога:** в `source` используем `export_format_version` (из файла), `source_server_version` (из API), а для `manual` не требуем версию. Старое `zabbix_version` допускается **только как входной устаревший псевдоним**, при сохранении не пишется. Один нормализованный каталог соответствует одному исходному шаблону (ADR-012).

**Два профиля каталога:** `portable_with_public_keys` (реальные безопасные ключи после проверки) и `redacted_aliases` (псевдонимы, без ключей). Для второго нельзя обещать автоматическое разрешение в новом корпоративном контуре без локальной таблицы или ручного подтверждения. Даже имена каталогов/заголовки могут содержать внутреннюю информацию; «переносимый» не тождественен «одобренный к внешнему обмену».

**Связь:** метрика в проекте ссылается на пару `catalog`/`metric`. `roles` не содержат реальные hostnames и IDs. Одна роль — `one` или `many`, разные роли могут указывать на один и тот же хост; дублирование по намерению пользователя не удаляем автоматически, только предупреждаем.

**Процедура развертывания:** проверка схем → проверка всех относительных каталогов → привязка ролей к стабильным слотам хостов → поиск по точному ключу на выбранных хостах (включая метрики, созданные непосредственно на хосте) → проверка типа/единиц/состояния → разрешение проблем вручную → развёртывание повторов → размещение → сравнение с целью → публикация.

Используем единый словарь `ResolutionOutcome` из ADR-003. Для отсутствующего `key` или неизвестного значения параметров, порождённых LLD, не делаем сопоставление по текстовому сходству. Для автономной работы сервер не нужен вообще; для публикации реальные ID обязательны. Импорт Zabbix YAML/JSON/XML — только локальное чтение, никогда не вызывает `configuration.import` и не назначает шаблоны хостам.

**Открытые проверки P0:** поведение существующих references, фактическая семантика `widgetid` на конкретной установке 7.4, контракт сохранения полей, встречающиеся в реальных панелях виджеты, корректность импортов из настоящих пользовательских шаблонов. До этого записи ограничены лабораторными сценариями.

### Дополнение v0.5 к ADR-005

`MetricCatalog.source.zabbix_version` — метаданные версии **исходного шаблона**, не жёсткое ограничение `7.4`. Каталог может происходить из файла версии 6.0, проект оставаться `project/v1`, а публикация выполняться через Zabbix 7.4 только после нового сопоставления. Парсеры экспортов разных версий разделены и не получают доступ к API. См. ADR-011.
